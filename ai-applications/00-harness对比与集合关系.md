## 0. 先给结论

**本文里的「AI 办公」= WorkBuddy / DuMate 这类产品：全能工作搭子（电脑/工作 Agent），不是邮件日历中台、也不是单一 SaaS 套件。**

在这个口径下：**Vibe Coding ⊂ AI 办公**——工程交付是父集能力之一；文档、浏览、表格、沟通、本地文件整理等属于 **通用工作剖面**。Cursor / Claude Code / 秒哒等是把 VC 子集 **抽成专精产品**，不等于与 AI 办公平级分立。

| 命题 | 判断 |
|------|------|
| **品类**：Vibe Coding ⊂ AI 办公（WorkBuddy/DuMate 向）？ | **是。** 父集是「代行知识与事务工作的 Agent」；VC 是其中的工程交付能力 |
| **品类**：AI 办公 = 中台/套件连接器？ | **否。** 那是另一条产品线；本文不把「AI 办公」收成中台 |
| **Harness**：父集是否「一套工具打天下」？ | **否。** 同一产品内仍要按任务切换世界剖面（VC 用 repo+shell；通用工作剖面用连接器/GUI/浏览器等），共享内核 `U` |
| **Harness**：父集产品「会一点代码」= 完整 VC？ | **未必。** 子集关系在品类上成立；工程 ACI 深度仍看是否真有 `V`（见 §3.1） |
| 和 SWE / Terminal-Bench？ | **无关直接等同。** 评测题库 ≠ 工作搭子品类 |

```text
AI 办公（WorkBuddy / DuMate 向 · 工作搭子）
├── 通用工作 / 文档 / 浏览 / 表格 / 沟通 / 本地整理 …
└── Vibe Coding …………………… repo · shell · 测/预览     ← 子集

专精抽出：Cursor / Claude Code / Codex / 秒哒 ≈ 只做（或主做）VC 子集
```

```text
              ┌──────────────────────────────────┐
              │  AI 办公（工作搭子父集）            │
              │  WorkBuddy · DuMate · …           │
              └────────────────┬─────────────────┘
         ┌─────────────────────┼─────────────────────┐
         ▼                     ▼                     ▼
  ┌─────────────┐    ┌─────────────────┐    ┌─────────────┐
  │ 通用工作/文档/…  │    │ Vibe Coding     │    │ …           │
  │              │    │ （子集）         │    │             │
  └─────────────┘    └────────┬────────┘    └─────────────┘
                              │ 可抽成专精产品
                              ▼
                     Cursor / Claude Code / 秒哒 …
```

## 1. 并排对比（父集内：VC 子集 vs 通用工作剖面）

对比的是 **同一类工作搭子产品内部** 的两种剖面，不是「搭子 vs 中台」。

| 设计轴 | Vibe Coding（⊂ AI 办公） | 通用工作剖面（文档/沟通/浏览/…） | 关系 |
|--------|--------------------------|--------------------------------|------|
| **主世界** | 工作区文件系统 + 终端进程 | 本地文件、浏览器、办公套件、IM… | 父集内多世界 |
| **ACI 形态** | Read/Edit/**Shell(cmd)**/Test；命令面偏工程 | **同一套控机思路**：cmd/Shell + 文件/GUI/浏览器等；**命令与动作面更宽** | 底层都是控计算机；差在词表广度与包装 |

| **Observation** | 每步常有 stdout/diff/测例（单步信号密） | 每步也是页面状态 / API /（必要时）用户确认；**单步信号相对疏**，靠 **多轮 ReAct 攒节点** | **都是多轮 ReAct**；疏的是单步信息量，不是「一轮就结束」或「只能写死脚本」 |
| **Done 定义** | 可运行/测过/预览达标 | 任务完成、交付物就绪、流程到达终态 | 都要可核对 |
| **真相源** | 磁盘与命令 | 应用状态 ∩ 权限 | 同构：世界 > 嘴上说的 |
| **权限** | 沙箱、命令确认、Plan | 账号授权、外发/支付等审批 | 父集产品要统一权限壳 |
| **记忆** | 项目约定、会话压缩、repo 再读 | 个人/工作偏好、跨 App 台账 | 父集记忆需分域 |
| **编排 / 时间性** | 偏 **前台陪伴式**：人在会话里推一轮；也有长会话与后台 shell，但产品重心仍是「坐下来改」 | 偏 **长程 + 后台**：跨小时/天的台账、定时巡检、收件箱盯梢、异步办结再通知 | **父集更重后台与跨会话**；VC 子集可挂长任务，但不是搭子主叙事 |
| **误操作代价** | 常可 git 回滚 | 外发/误操作难回滚 | 通用工作剖面默认更保守 |
| **Code** | 一等公民 | 旁路（洗数等） | 其它能力 ≠ 自动长出完整 VC |
| **典型形态** | 搭子内的「写代码模式」；或抽成 Cursor/秒哒 | WorkBuddy/DuMate 的主叙事能力面 | VC ⊂ 搭子品类 |

### 1.0 通用工作剖面也是多轮 ReAct（不是「稀疏观察 → 只能脚本」）

表里的「页面状态、API、用户确认」描述的是 **单步 Observation 长什么样**，不是执行模型。

| 误解 | 更准确 |
|------|--------|
| 通用工作剖面 = 单次工具调用 + 稀疏结果即结束 | 通用工作剖面 = **多轮 ReAct**：拆解子任务/节点，逐步观察后再决策 |
| 反馈疏 ⇒ 只能预写脚本/工作流 | **开放任务仍走 Agent 环**；脚本/SOP 图是可选加速，不是唯一实现 |
| 用户确认替代了 ReAct | 确认只是某些节点的 **闸门 Observation**；前后仍是多步 tool 环 |
| 和 VC 的差别是「有没有 ReAct」 | 差别是 **世界与单步信号密度**；两边都是 ReAct（可再套长程 job） |

```text
通用工作任务（示例：汇集材料 → 起草回复 → 等待确认 → 发送）
  节点1  ReAct*: 打开页/调 API → 读状态 → …
  节点2  ReAct*: 生成草稿 → 写回系统
  闸门   Observation = 用户确认（疏、但关键）
  节点3  ReAct*: 发送 / 归档 → 核对终态
  * 每个节点内部仍是多轮：act → observe → act …

VC 任务则同一骨架，只是 Observation 更常是 diff/测例（单步更密）。
```

**脚本/工作流的位置**：已知 SOP（每周五汇总）可用预定图减少探索；遇上变体、异常页、要临场决策时，仍回落到多轮 ReAct。搭子 harness = **ReAct 主路径 +（可选）SOP 短路 + 长程 job 壳**，不是「只能脚本」。

### 1.0b 长程与后台（父集相对 VC 的显性差）

你的判断成立：**AI 办公（工作搭子）应更重长程任务与后台任务**；VC 更多是高带宽前台环，偶尔才把构建/测试丢到后台。

| | Vibe Coding 子集 | AI 办公父集（通用工作剖面 + 可含 VC） |
|--|------------------|------------------------------|
| **典型时钟** | 分钟～数小时的连续会话 | 小时～天～周；人离开后仍在推进 |
| **启动方式** | 几乎总是人开口（或 IDE 里点一下） | 人开口 **+** 日程/邮件/文件变更/cron **主动拉起** |
| **状态载体** | 会话上下文 + repo；进阶才有 progress 文件 | **任务台账 / 待办队列 / 订阅规则** 一等公民 |
| **后台形态** | 后台命令、远程 agent、过夜改码（有，但是加分项） | 盯邮件、催办、定时汇总、多步流程挂起等确认——**主能力** |
| **人机节奏** | 人常在线看 diff/预览 | 人可离线；关键节点推送/汇总再介入 |
| **和子集关系** | 长程 coding 是 VC 的进阶 | 父集把「长程/后台」做成平台能力后，VC 长任务也可挂在同一队列上 |

```text
VC 常见：  人 ──会话──▶ Agent ──前台环──▶ 交付（人还在）
搭子常见： 触发/人 ──入队──▶ 后台跑 / 等外部事件 ──▶ 通知人确认 ──▶ 续跑或办结
```

Harness 含义：父集要优先投资 **durable job、唤醒、通知、跨会话 ledger**；只把 ReAct 做在前台 Chat 里，搭不出 WorkBuddy/DuMate 体感。

### 1.0c 验收与检验：为何难「代码单测化」

**成立：AI 办公（尤其通用工作剖面）很难像 VC 那样，用仓库单测 / CI 绿作为主检验形态。**

| | Vibe Coding 子集 | 通用工作剖面（及含它的搭子父集） |
|--|------------------|----------------------------------|
| **天然 oracle** | 单测、类型检查、构建、预览——**机读、可重复、可进 CI** | 少有等价物；「邮件是否得体」「材料是否找齐」难写成 `assert` |
| **状态是否可钉死** | repo + 容器可复现 | 多 App、账号、页面、时效数据；环境漂移大 |
| **副作用** | 多可回滚（git / 沙箱） | 外发、改日历等难回放「再跑一遍单测」 |
| **长程/后台** | 仍可对最终 patch 跑测 | 跨天 job、等人确认——时间轴不适合经典单测夹具 |
| **产品内闭环** | Agent 自己跑测当 Observation | 常依赖确认闸门、人工抽检、业务规则，而非红绿测例 |

这不是「做不出 Agent」，而是 **检验形态必须换**：

```text
VC 主检验：     改码 → 跑测/构建 → FAIL/PASS（单测思维可迁移到 Agent 环内）
办公主检验：   多轮 ReAct → 状态/交付物核对 →（关键步）人确认
               评测侧另建：仿真世界 / 黄金轨迹 / 规则断言 / LLM-as-judge（慎用）
```

| 仍可自动化的部分 | 说明 |
|------------------|------|
| 连接器与权限壳 | OAuth、RBAC、工具 schema、审计日志——**适合传统单测/集成测**（测 harness，不测「事是否办对」） |
| 钉死仿真世界 | 如 APEX 类：虚构文件树 + 固定 App 工具，对规定交付物断言——**评测用**，成本高 |
| 黄金脚本 / 契约测 | 已知 SOP 的终态检查（字段是否写入、邮件是否进入 sent）——覆盖窄 |
| 轨迹回归 | 固定输入下 tool 序列/关键节点是否触发确认——测策略稳定性 |
| 人审 / 抽检 | 开放任务的主真理源之一 |

**工程含义**：不要幻想「给办公 Agent 写一套像 Jest 一样的业务单测就闭环」；应把预算拆成——**(1) harness 可单测**（工具、队列、闸门），**(2) 能力评测用仿真/黄金集**，**(3) 线上靠确认与抽检**。VC 子集仍可继续用测例 oracle。

### 1.1 Tool / MCP / Skill / System Prompt 倾向

#### 先纠正：二者都在用 cmd 控机

**WorkBuddy / DuMate 口径下，VC 与通用工作剖面的共同点是：通过命令与系统动作控制计算机**（Shell/cmd、进程、文件系统；常再加 GUI/浏览器自动化）。  
不是「VC 用 cmd、办公改走另一套纯 API 宇宙」。差在：

| | Vibe Coding 子集 | 通用工作剖面（父集主叙事） |
|--|------------------|---------------------------|
| **控机方式** | cmd + 读写工作区（为主） | **同样** cmd/系统动作，并叠加更多 App/GUI/浏览器操控 |
| **命令词表** | 相对窄：git、包管理、构建、测试、语言工具链 | **更宽**：文件整理、系统工具、多应用启动与操作、下载/同步、脚本化日常事务… |
| **「更多」指什么** | 深度：长链路工程命令、测例闭环 | **广度**：命令/动作种类与目标应用更多，且常跨 App |
| **包装层** | Edit/Grep 等是对 FS 的结构化壳 | MCP/连接器/GUI tool 也是壳——底层仍常落到进程、URI、快捷键、AppleScript/`osascript`、`xdotool` 等 |

```text
共享根基：Agent →（工具壳）→ 计算机（cmd / FS / 窗口 / 浏览器）
VC：     词表 ≈ 工程 CLI + repo
办公：   词表 ≈ 工程 CLI 的超集 + 桌面/办公/浏览器动作（更广）
```

结构化 Tool / MCP **不否定 cmd**，而是：给高频危险动作加 schema、鉴权与确认；实现上仍可能是「受控地执行一条命令或一次系统调用」。

| 扩展面 | Vibe Coding（子集）倾向 | 通用工作剖面倾向 |
|--------|--------------------------|-------------------------|
| **Builtin / 控机** | Shell/cmd **一等**；词表偏工程 | Shell/cmd **同样一等**；词表 **更广**，并重 GUI/文件/多 App |
| **MCP** | 加插件（浏览器、Issue…） | 扩展面更大：把常用应用与系统能力接进同一控机环；更要工具发现 |
| **Skills** | 工程流程、框架惯例、排障剧本 | 跨应用业务流程 SOP、个人工作流；按需加载 |
| **System Prompt** | 何时跑测、改码红线、工程规则文件 | 人设、模式切换、**高风险命令/外发确认**、长程任务纪律 |

**一句话**：二者都是 cmd/系统动作驱动的计算机 Agent；AI 办公是词表更宽的父集控机，VC 是其中偏工程交付的窄词表子集。

#### 权限与包装（不是「办公禁用 cmd」）

| 形态 | 含义 |
|------|------|
| 开放高危 cmd 无门禁 | 两边都不该默认（`rm -rf`、批量外发脚本等） |
| 受控 cmd + allowlist / 确认闸门 | **办公与 VC 的共同生产形态** |
| MCP / 结构化 Tool | 对常用动作的 schema 化；底层仍常是控机 |
| 纯聊天不落系统 | 两边都不是工作搭子 |

```text
搭子 · 通用工作剖面（多轮 ReAct）
  → 更广的 cmd / GUI / 文件动作 → 页面或命令输出观察 →（高风险）确认 → …

搭子 · VC 子集（多轮 ReAct）
  → 工程向 cmd / Edit / Test → diff/测例观察 → …

共享：U + 同一台（或同一类）计算机控制面；办公侧命令/动作覆盖 ⊇ VC 常用子集（再外加大量非工程动作）
```

## 2. 交集（两边 harness 都得有的）

下面这些是 **应用无关的 harness 内核**；缺了就两边都会废：

| 交集能力 | 说明 |
|----------|------|
| **Agentic Loop** | 选工具 → 执行 → 观察 → 再推理 |
| **计算机控制面** | 通过 cmd/系统动作（及封装后的 Tool）改真实环境；办公词表更广，VC 是其工程向窄化 |
| **工具结果回流** | Observation 结构化进上下文，而不是只聊天 |
| **上下文治理** | 预算、压缩、稳定前缀与易变后缀分离 |
| **可中断权限门** | 危险动作可拦、可问人 |
| **会话/任务状态** | 多轮或跨会话不丢目标；父集还要把状态升级成可后台调度的 job |
| **可观测性** | trace / 事件流，便于调试与评测采样 |
| **模型可替换** | 能力在 harness，不绑死某一模型品牌 |

父集相对 VC **加码**（仍可复用到 VC 长任务，但办公侧更刚需）：**durable 队列、定时/事件唤醒、人离线后的进度与通知、跨天 ledger**。

也存在 **表层重叠的动作**（易误判成「一个是另一个的子集」）：

| 表面相似 | 为何仍不算 ⊂ |
|----------|----------------|
| 都用 cmd 控机 | **成立且应强调**：共享根基；办公命令/动作面 ⊇ VC 常用工程命令，再加大量非工程控机 |
| 都改「文档」 | VC 改源码树文件；通用工作剖面还涉及套件文档、本地整理等 |
| 都跑代码 | VC 为交付软件；通用工作剖面多为分析/自动化脚本 |
| 都有 Plan | VC 防乱改仓库；办公常对接确认闸门与 SOP |

## 3. 差集（只在一侧成为一等设计）

### 3.1 几乎只有 Vibe Coding 一等化的

- 大仓导航与结构化代码编辑  
- 本地/沙箱 Shell、包管理、CI 风格验证环  
- 以 **测试/类型检查/预览** 为密反馈 oracle  
- 工程规则文件（`AGENTS.md` / 工程 Skill）驱动的 repo 惯例  
- 「应用生成 + 热预览」类产品闭环（秒哒式）

### 3.2 几乎只有「通用工作剖面」一等化的（仍在 AI 办公父集内）

- 多 App / 浏览器 / 本地整理的非仓库世界  
- **草稿 → 确认 → 外发** 一类高副作用门  
- 跨应用台账与个人工作记忆分域  
- 主动式 / 定时「帮我盯着」  
- **长程任务台账 + 后台执行 + 办结通知**（相对 VC 更一等公民）  
- 按当前任务装载工具面（toolbelt），避免 coding+通用工作工具一次性灌满  

（中台级多租户 RBAC、连接器中台等是 **另一产品线**，不是 WorkBuddy/DuMate 口径的必选项。）

## 4. 子集 / 交集关系（严格一点画）

### 4.1 两层集合（推荐心智）

```text
【品类层】
AI办公 := WorkBuddy / DuMate 向工作搭子（通用工作 Agent）
VibeCoding ⊂ AI办公
专精VC产品（Cursor/Claude Code/秒哒…）≈ 把子集抽成独立 App

【Harness 层】
U = 通用内核（§2）
V = VC 专用（§3.1）
W = 通用工作剖面专用（§3.2）…… 非「中台」的意思，而是搭子里非 coding 能力

AI办公Harness（理想完整） ≈ U ∪ V ∪ W ∪ …
仅覆盖通用工作剖面的弱实现           ≈ U ∪ W          （品类上仍叫办公，但 VC 子集很浅）
专精 VC                    ≈ U ∪ V

因此：
  品类上  VC ⊂ AI办公（WorkBuddy/DuMate 向）   ✓ 你的口径
  实现上  完整搭子应能挂上 V；只有 W 不算真包含 VC 深度
```

### 4.2 易混说法

| 说法 | 怎么判 |
|------|--------|
| 「Vibe Coding 是 AI 办公的子集」 | **成立**——AI 办公 = 工作搭子父集，不是中台 |
| 「AI 办公 = 邮件日历中台」 | **不是本文口径**；那是另一条线 |
| 「搭子会跑两行 Python = 已有 VC」 | **深度不够**；要看是否具备 §3.1 的工程 ACI |
| 「Cursor 与 DuMate 平级互斥」 | **品类上不必**；Cursor 更像 VC 子集的专精抽出 |
| 「SWE-bench ⊂ Vibe Coding」 | SWE 是评测；VC 是能力/产品范式 |
| 「Terminal-Bench = AI 办公」 | TB 是终端综测，≠ 工作搭子品类 |

### 4.3 产品路线

```text
1) 工作搭子父集：统一会话/权限壳 + 多世界剖面（通用工作剖面 ‖ VC ‖ …）
```
