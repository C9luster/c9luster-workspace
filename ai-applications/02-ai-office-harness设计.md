# AI 办公：Harness 设计

> 本文口径的 **AI 办公 = WorkBuddy / DuMate 向工作搭子**（通用工作 Agent），**不是** 邮件日历中台或单一 SaaS 套件。  
> **Vibe Coding ⊂ 本父集**；下文主写父集的「通用工作」剖面与多世界挂载，工程子集细节见 [01-vibecoding-harness设计.md](./01-vibecoding-harness设计.md)。

---

## 1. 一句话定位

**AI 办公 harness = 个人/团队工作搭子的 ACI**：在 **同一会话壳** 下，按任务切换世界——通用工作（文件/浏览器/套件/IM）、以及作为子集的 vibe coding（repo+shell）。正确性靠 **任务完成可核对 + 高风险确认**；VC 子集另外靠测/预览。

```text
用户自然语言（或主动触发）
    → 统一权限壳 / 记忆分域 / 工具发现
    → 路由到世界剖面，均为多轮 ReAct：
         · 通用工作剖面：拆节点 → Tool/MCP/GUI → 页面/API 观察 → … →（关键节点）确认闸门 → 续跑
         · VC 子集：Edit/Bash/Test → diff/测例 → …
    → 可挂长程 job（人离开后唤醒续跑）
    → 交付：任务完成，或代码可运行/可预览
```

---

## 2. Harness 要回答的六个设计问题

| 问题 | AI 办公的典型答案 |
|------|------------------|
| **世界是什么** | 多 SaaS / 办公套件 + 共享盘 + 组织目录；状态分散、最终一致 |
| **动作空间** | 邮件、日历、文档、表格、PDF、IM、任务板、CRM…；偶含代码执行做计算 |
| **什么叫做完** | 指定交付物存在且合规（稿已发、表已改、会已约）；常需人确认 |
| **真相源** | 各系统 API 返回值 + 权限边界；对话不能覆盖「实际有没有发出去」 |
| **失败怎么回** | API 错、冲突日程、权限不足、草稿被拒 → 重试 / 改写 / 升级人工 |
| **谁能拦一刀** | OAuth scope、RBAC、审批队列、审计、外发限额、敏感数据策略 |

## 3. 分层心智模型

```text
┌──────────────────────────────────────────────┐
│ 产品壳：侧边栏助理 / 任务收件箱 / 会议纪要入口   │
├──────────────────────────────────────────────┤
│ Harness 内核                                  │
│  · 长程 Loop + 任务台账（ledger）              │
│  · 身份 / 租户 / 连接器凭证                    │
│  · 工具发现（toolbelt）与上下文隔离            │
│  · 草稿 → 审批 → 执行                         │
│  · 审计与可回放                                │
├──────────────────────────────────────────────┤
│ 连接器层：Mail / Calendar / Docs / Sheets / … │
├──────────────────────────────────────────────┤
│ 模型（可换）                                  │
└──────────────────────────────────────────────┘
```

与「只做 VC 的专精产品」相比：搭子父集必须 **多世界可切换**；VC 是其中一块，不是唯一 Runtime。中台多租户不是本口径的前提。

## 4. 典型能力模块

### 4.1 工具面（多应用 ACI）

| 能力族 | 作用 | 设计要点 |
|--------|------|----------|
| 通信 | 读线程、起草、发送、跟进 | **默认草稿 + 审批**；发送是高权限动作 |
| 日程 | 查忙闲、创建/改期、会议室 | 冲突检测；时区与委托人 |
| 文档 / 幻灯 | 读写结构化内容 | 版本与协作锁；引用溯源 |
| 表格 | 查询、透视、回写单元格 | 公式/类型校验；防整表误覆写 |
| 文件 / PDF | 归档、检索、摘要 | 命名规范与权限继承 |
| 元工具 | 发现工具、读 schema、规划 todo | 工具太多时避免一次性塞满 prompt（APEX 式 toolbelt） |
| 可选 Code / VC 子集 | 洗数；或进入完整工程环 | 浅 code ≠ 已覆盖 VC；完整子集见 01 文 |


### 4.2 上下文与记忆

| 层 | 常见形态 | 用途 |
|----|----------|------|
| 身份上下文 | 用户、角色、委托、租户 | 决定可见数据与可调 API |
| 对象上下文 | 当前客户 / 项目 / 案件「世界」 | 按触发动态装载，避免全家桶 |
| 工作记忆 | 任务台账、待审批项 | 跨天、跨会话的流程连续性 |
| 组织记忆 | 话术、归档规范、模板 | 需权限与新鲜度，不能当全局可写 |
| 压缩 / 摘要 | 长线程与多文件摘要 | 办公轨迹更长、更碎，更依赖结构化摘要 |

关键原则：**按「操作对象」隔离上下文**（客户 A 的邮件不要污染客户 B 的推理）。

### 4.3 编排

- **主 Agent + 专项子 Agent**：检索、制表、写长文、合规检查可拆开。
- **多轮 ReAct 推节点（默认）**：打开 → 读状态 → 改 → 再读 → …；「页面/API/确认」是每步观察，不是整单任务只看一次。
- **预定工作流 + Agent 填槽（可选短路）**：固定 SOP（如周报）用图/状态机减探索；异常与开放目标仍回 ReAct。
- **人在环（HITL）**：外发、改主数据、批量删除是闸门节点，插在多轮环中间，不替代环本身。
- **长程 / 后台（父集主叙事）**：任务入队 → 人可离开 → 事件/定时唤醒续跑 → 推送摘要或求确认 → 办结写回台账。VC 子集的「过夜改码」可挂同一套 job 壳，但搭子产品不能只靠前台 Chat 会话。
- **主动式 / 定时触发**：日程提醒、收件箱分流——相对专精 VC 产品更常「非对话启动」。

### 4.4 权限、审批与审计

```text
模型提议 tool_call
    → harness 鉴权（scope ∩ RBAC ∩ 策略）
    → 若高风险：写入审批队列，不直接执行
    → 人通过后再执行
    → 写审计：谁、对何对象、何时、结果
```

没有审计与可归因执行，办公 harness 很难进生产。

## 5. 「做对了」如何定义

| 类型 | 例子 | 判据 |
|------|------|------|
| 工件交付 | 生成/修改 doc、xlsx、ppt | 文件内容与任务说明对齐（可规则 + 抽检） |
| 通信闭环 | 回复客户、催办 | 线程状态变化；常需人最终确认 |
| 流程办结 | 入职、报销、排期 | 下游系统状态机到达终态 |
| 专业评测（研究向） | APEX-Agents 等 | 钉死「世界」+ 规定交付物 + 可复现环境 |

注意：通用工作剖面 **缺少** 像 SWE-bench / 仓库 CI 那样普遍的「单测 oracle」。产品与评测要分轨：harness（工具、队列、确认闸门）可单测；任务是否「做对」更多靠 **仿真世界、黄金终态、抽检与确认**，而不是把业务对错塞进 Jest。详见 [00 §1.0c](./00-harness对比与集合关系.md)。

## 6. 设计上的强约束（相对「只做 VC」）

1. **同一控机根基、更宽词表**：通用工作剖面与 VC 都靠 cmd/系统动作；办公侧命令与 GUI 动作覆盖更广，并要有确认闸门。  
2. **必须能进入工程剖面**：词表不能锁死在非工程动作；进入 VC 时要有完整 Shell/测例环。  
3. **副作用出界**：误发/误点难 `git reset`。  
4. **工具面按任务装载**：避免通用工作工具+全量工程工具同时灌爆上下文。  
5. **统一权限壳**：确认门覆盖外发与危险命令。  
6. **记忆分域**：个人偏好 / 当前项目 / 工程约定不要糊成一团。

---

## 7. 反模式

| 反模式 | 问题 |
|--------|------|
| 把 AI 办公定义成中台连接器清单 | 偏离 WorkBuddy/DuMate 口径；VC 子集无处安放 |
| 只有浅 code exec 却宣称已含 vibe coding | 品类上「能沾边」，深度上未覆盖 `V` |
| 工具 schema 全量塞进每一轮 | 选错率与耗 token 双高 |
| 自动外发默认开 | 信任与事故成本不可接受 |
| 通用工作剖面与工程交付共用一份无隔离 memory | 串上下文、串权限 |
| 用 LLM 裁判替代系统/UI 状态核对 | 「我说做了」≠ 真做了 |
