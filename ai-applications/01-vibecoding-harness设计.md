# Vibe Coding：Harness 设计

> 本文描述 **Vibe Coding 应用层** 的 harness 该长什么样：模型外面那一层如何把「自然语言目标」变成可迭代的工程动作。  
> 不绑定某一家 CLI；秒哒 / Claude Code / Codex / Cursor 等是不同产品实现，共享的是同一类设计问题。

---

## 1. 一句话定位

**Vibe Coding harness = 面向软件工件的 ACI（Agent–Computer Interface）**：让模型在 **仓库 + 终端 + 预览/测试反馈** 里闭环改世界，而不是只生成一段代码文本。

```text
用户自然语言
    → harness 组装上下文 / 权限 / 工具面
    → 模型选工具（读、搜、改、跑）
    → Runtime 执行 → Observation 回流
    → （压缩 / 记忆 / 子 Agent）→ 下一轮
    → 交付物：可运行代码 / patch / 应用预览
```

---

## 2. Harness 要回答的六个设计问题

| 问题 | Vibe Coding 的典型答案 |
|------|------------------------|
| **世界是什么** | 工作区（repo / 项目沙箱）、进程、网络（常受限）、可选浏览器/预览 |
| **动作空间** | 文件读写与结构化编辑、搜索、Shell、测试/Lint、包管理、Git；常加 MCP |
| **什么叫做完** | 行为可验收：测例绿、预览符合描述、构建通过；产品侧也可是「用户点满意」 |
| **真相源** | 磁盘上的代码与命令输出优先于对话措辞；对话只是意图 |
| **失败怎么回** | stderr、失败测试、类型错误、diff 冲突 → 进入下一轮 ReAct |
| **谁能拦一刀** | 权限模式、沙箱、危险命令确认、Plan Mode、hooks |

## 3. 分层心智模型

```text
┌─────────────────────────────────────────┐
│ 产品壳：Chat / IDE / 云 IDE / App 生成器 │  ← 交互与多模态入口
├─────────────────────────────────────────┤
│ Harness 内核                             │
│  · Agentic Loop（step / queryLoop）      │
│  · 上下文：system + 规则文件 + 历史压缩   │
│  · 工具面与权限门                        │
│  · 会话 / 记忆 / 子 Agent                │
├─────────────────────────────────────────┤
│ Runtime：沙箱 FS + Shell (+ 浏览器)      │
├─────────────────────────────────────────┤
│ 模型（可换）                             │
└─────────────────────────────────────────┘
```

要点：**换模型 ≠ 换 harness**；换 harness 才改变「能看见什么、能改什么、怎么验收」。

---

## 4. 典型能力模块

### 4.1 工具面（ACI）

| 能力族 | 作用 | 设计要点 |
|--------|------|----------|
| 导航 / 搜索 | 在大仓里定位 | 结果截断、先列文件再给细节，避免一次灌爆上下文 |
| 编辑 | 改源码 | 优先结构化 patch / 编辑工具，而不是整文件重写 |
| Shell | 构建、测、装依赖 | 沙箱 + 超时 + 输出截断 |
| 验证 | test / lint / typecheck | 把「对不对」变成可机读 Observation |
| 扩展 | MCP / Skills / Hooks | 产品差异化主要发生在这里 |

### 4.2 上下文与记忆

| 层 | 常见形态 | 用途 |
|----|----------|------|
| 稳定前缀 | System + 工程规则 / `AGENTS.md` / `CLAUDE.md` | 可缓存、少变 |
| 工作记忆 | 当前任务、打开文件、todo | 跨轮连贯 |
| 压缩 | snip / compact / condenser | 长会话不爆窗 |
| 长期记忆 | memdir / Memories / 项目笔记 | 跨会话偏好与约定 |
| 仓库真相 | 再读文件、再跑命令 | 防幻觉「以为改过了」 |

### 4.3 编排

- **单主 Agent ReAct**：大多数 Vibe 会话的默认形态。
- **子 Agent / 并行探索**：调研、大范围搜索、隔离脏上下文。
- **Plan → 执行**：先规划后改码，降低乱改面。
- **Initializer / progress 文件**（长任务）：跨会话续作（如 progress.txt + git）。

### 4.4 权限与安全

- 文件系统边界（工作区 / 沙箱）
- 网络与密钥隔离
- 命令 allow/deny、人工确认
- 不可逆操作（`rm -rf`、force push、生产写）默认高摩擦

## 5. 与「脚手架产品」的关系

| 层级 | 例子 | 和本文关系 |
|------|------|------------|
| 应用范式 | Vibe Coding | **本文** |
| Coding Agent 脚手架 | Claude Code、Codex、OpenHands、秒哒 Ada | harness **实现** |
| 统一运行时 | AgentWay 等多 harness 网关 | 托管多种 coding harness，不定义办公语义 |

秒哒链路可作具体参照（细节见内部 `AgentArchitecture`）：

```text
自然语言 → EventStream → EngineeringRules / Condenser / Memory
        → LLM Function Calling → Runtime → Observation → …
```

产品差异往往在：**规则硬路由、PRD/选区/报错注入、App 预览验收**，而不是「有没有 ReAct」。

---

## 6. 设计上的强约束（作为 AI 办公的子集时）

1. **可执行反馈密集**：几乎每一步都能跑命令或看 diff。  
2. **世界状态高度可观测**：`cat` / `git diff` / 测试日志。  
3. **进入本子集才强调开发机 Runtime**；在搭子父集里由统一壳路由进来。  
4. **交付物偏可运行软件**；与「发消息/改在线文档」的 Done 定义分开。

---

## 7. 反模式

| 反模式 | 问题 |
|--------|------|
| 只有 Chat，没有 Runtime | 退化为代码补全，不是 Vibe Coding harness |
| 工具无限膨胀且无发现机制 | 选工具比干活还烧 token |
| 不以仓库/命令为真相 | 模型「口头修好」但磁盘未变 |
| 无压缩的超长会话 | 中后期指令遵循崩塌 |
| 把评测 oracle（如 SWE F2P）当成产品体验标准 | 产品要的是体感与交付，评测要的是可复现分数 |
