# 01 — 数据集构建与性质（SWE-bench × Terminal-Bench）

构建 Agent benchmark 不是「写几道题 + 跑一遍模型」，而是同时设计：**选题从哪来、能力/领域如何覆盖、环境如何复现、什么叫对、如何防作弊、如何持续更新**。SWE-bench 与 Terminal-Bench 代表两条主流路线——**从真实软件工程轨迹挖掘** vs **手工构造可验证终端任务**。

---

## 0. 选题从哪来 × 覆盖广度总览（先读）

### 0.1 选题来源对比

| | SWE-bench | Terminal-Bench |
|--|-----------|----------------|
| **谁选题** | 流水线从 GitHub **自动挖**；人主要定仓名单与过滤规则 | **人写 / 社区投稿**；评审按 rubric 收题 |
| **题从哪冒出来** | 已 merge、且修了 Issue、且带测试改动的 PR | 作者认为「终端里有人愿付钱做」的真实难题 |
| **覆盖面怎么控** | 由所选仓库与时间窗决定（偏 Python 仓修 issue） | 由投稿领域与策展决定（系统/安全/科学/工程等更杂） |
| **入集门槛** | 属性过滤 + **执行验证**（必须有 FAIL_TO_PASS） | Oracle 可解 + verifier 客观 + **对抗审查**（反 hack） |
| **不是选题的方式** | 不为「凑题」手写假 issue | 不为「哄模型过」写成 prompt；忌纯 clerical 步骤题 |

理解：SWE 的「选题」≈ **哪些真实 PR 配得上当考题**；TB 的「选题」≈ **哪些终态任务值得放进终端综合考场**。两者都不是 vibe coding / AI 办公题库。

### 0.2 覆盖度（Coverage）及相关概念

**覆盖度（Coverage）** 指：在预先定义的能力或任务维度上，数据集是否包含足够、均衡的实例，使评测结论能反映所声称的 **Agent 能力/任务空间**，而非单一子场景。**广度（Breadth）** 常与 Coverage 同义使用。**代表性（Representativeness）** 则强调样本分布与目标真实场景是否一致。**构念覆盖（Construct coverage）** 关注单一 benchmark 所对应的构念（construct）是否在多个子面上被采样。

| 概念 | 在问什么 | 典型做法 |
|------|----------|----------|
| **Coverage（覆盖度）** | 各预设维度是否有题、空白维度是否过多 | 能力 taxonomy、分层配额、策展平衡 |
| **Representativeness（代表性）** | 实例分布是否贴近真实工作负载 | 选仓策略、领域权重、剔除偏门刷分题 |
| **Construct coverage** | 构念是否被多子面覆盖 | SWE 以「修 issue」为主、单构念较深；TB 终态类型更杂 |

Coverage 与 **Reliability（可靠）**、**Reproducibility（可复现）**、**Anti-hacking（防作弊）** 等性质相区分（见 §5）：后者保证「同一题、同一解」的判分一致；Coverage 保证「整套题」未系统性遗漏某类能力或场景。题集可以 reliability 高而 coverage 低（稳定但窄），也可以 coverage 高而单题判分噪声大——二者需分别设计。

| 覆盖维度 | SWE 怎么扩 | TB 怎么扩 |
|----------|------------|------------|
| **领域 / 栈** | 加仓（框架、库、语言）；Multilingual 等衍生 | 投稿覆盖系统、安全、数据、科学、工程等 |
| **任务形态** | 基本是「Issue → patch」一种交付 | 文件/服务/协议/编译/调试等多种终态 |
| **难度层** | Full vs Lite vs Verified（深而专） | difficulty、expert_time 元数据 + 策展 |
| **规模与推理** | 大仓、多文件 PR 自然出现 | 选题时刻意要「仓级/系统级」而非 clerical |
| **防「假广」** | 加仓≠加玩具仓；仍要 FAIL_TO_PASS | 拒纯步骤剧透、纯磨资源；广在概念多样 |

推荐构建顺序：**明确能力/领域 taxonomy → 确定选题规则（挖掘 vs 手工）→ 以配额或策展填补空白维度 → 单题 validity/reliability 等按 §5 独立验收。**

### 0.3 两条路线的覆盖扩展（对照）

```text
SWE-bench
  广度杠杆 = 仓清单 × 时间窗 ×（可选）语言/模态衍生集
  风险     = 看似很多实例，但构念仍是「Python 开源仓 + 测试驱动修 bug」
  补洞方式 = 加仓、SWE-bench Multilingual、换子集过滤强度（Lite/Verified 偏深不偏广）

Terminal-Bench
  广度杠杆 = 社区投稿 + 元数据 category/difficulty + 版本集合稿
  风险     = 热门领域扎堆、clerical 题冒充多样
  补洞方式 = rubric 拒偏题 + 显式缺领域征稿 + Verified 修 hack 但不删领域维度
```

## 1. 两条构建哲学

| 维度 | SWE-bench | Terminal-Bench（Harbor 任务格式） |
|------|-----------|----------------------------------|
| 数据源 | 流行开源仓的 Issue / PR | 作者投稿的任务目录（instruction + env + oracle + tests） |
| 规模逻辑 | 爬取 → 属性过滤 → **执行验证** → 入集 | 设计 → Oracle 可解 → Verifier 客观 → 对抗审查 → 入榜 |
| 金标 | Gold patch（PR 非测试改动） | `solution/solve.sh`（Oracle Agent） |
| 评测面 | 「修 issue」：生成并应用 patch | 「完成目标」：进程/文件/协议等终态 |
| 更新方式 | 可对新仓/新 PR 重复流水线（anti-contamination） | 版本化数据集（如 2.0 → 2.1 Verified 修 hack） |
| 选题主权 | 规则 + 自动过滤（人定仓与阈值） | 人选题 + 社区评审（rubric 门禁） |

共同底线：**可执行、可复现、以结果而非过程为主判分**；单题还要可靠、防 hack（见 §5，与覆盖广度分开看）。

## 2. SWE-bench：如何从 PR 变成实例

### 2.0 选题规则（挖什么、丢掉什么）

```text
选仓（人）
  → 高下载 / 高维护 / 许可允许 / 测试较全的开源仓
  → 避免「玩具仓」：缺文档、缺 CI、PR 质量差则后续执行验证会大面积失败

刮 PR（自动）
  → 该仓历史上的 PR（可达数万～十万级）

属性选题（自动，决定「像不像一道题」）
  ✓ Merged          → 社区承认的改动，不是草稿
  ✓ 链接并修复 Issue → 有自然语言问题陈述，可当 prompt
  ✓ 改动测试文件     → 有机会得到可执行验收（FAIL_TO_PASS）
  ✗ 仅文档/格式/无 Issue / 未 merge → 直接不进 candidate

执行选题（自动，决定「配不配评测」）
  ✓ 环境可安装、测试可跑
  ✓ 至少 1 个 FAIL_TO_PASS（金标前后测试状态翻转）
  ✓ 无安装/运行错误淹没信号
  ✗ 无 fail→pass、法兰、依赖随机失败 → 丢弃

子集再选题（人 + 更严规则，如 Verified / Lite）
  → 去歧义 Issue、去过脆环境、去争议实例，提高可比性（子集更「深」不一定更「广」）
```

要点：**选题不是「挑一个有趣的 bug 故事」**，而是「PR 是否同时具备问题陈述、可执行测试预言机、可复现环境」。覆盖面由仓清单决定，扩展覆盖 = 加仓/加语言，而不是放宽 FAIL_TO_PASS。

### 2.1 三阶段流水线（论文核心）

```text
Stage I  选仓 + 刮 PR
         优先高下载/高维护 Python 仓；约数万～十万级 PR

Stage II 属性过滤 → candidate
         · status = Merged
         · 关联并解决一个或多个 GitHub Issue（标题/正文/commit 里的 fixes #N）
         · 改动了测试相关路径（含 test/testing 等关键词）→ 暗示有验收测试

Stage III 执行过滤 → evaluation instance
         · 按版本搭可安装环境
         · 先应用「测试补丁」，再分别在「仅测试 / 测试+金标补丁」下跑测
         · 至少存在 FAIL_TO_PASS（修前失败、修后通过）
         · 安装/运行错误、无 fail→pass 的丢掉
```

数量级直觉：约 90k PR → 过滤后约 2k+ 评测实例（随版本变化）。训练用数据可放宽「必须改测试」以扩大规模，但 **评测仓与训练仓应隔离**，减轻污染。

### 2.2 一个实例里有什么（模块）

| 字段 / 模块 | 作用 |
|-------------|------|
| `repo` + `base_commit` | 代码库快照 C |
| `problem_statement` | Issue 文本（Agent 看到的「需求」） |
| `patch`（gold） | 解决 issue 的代码 diff（不含或分离测试） |
| `test_patch` | 测试相关 diff |
| `FAIL_TO_PASS` | 必须被修好的测试列表 |
| `PASS_TO_PASS` | 回归：修完后仍应保持通过 |
| 安装规格 | 按 repo×version 的依赖与构建命令（镜像 / Dockerfile 生成） |

评测 harness 典型步骤：检出 base →（可选）应用 test_patch → 跑测记录失败 → 应用模型 patch → 再跑测 → 看 FAIL_TO_PASS / PASS_TO_PASS。

### 2.3 构建时必须盯住的模块

| 模块 | 注意点 |
|------|--------|
| **Collect**（`swebench/collect`） | `print_pulls` → `build_dataset`；Issue 链接解析要准 |
| **Version / Install map** | 错误环境 = 假阴性；需按 release 钉依赖 |
| **Validation engine** | 安装成功、测试可跑、存在非平凡 FAIL_TO_PASS |
| **Patch 分离** | 测试改动 vs 产品代码改动；避免「答案写在测试可见处」不公平 |
| **Harness 判分** | 解析测试日志映射到具体 case；日志格式随框架而变 |
| **Lite / Verified 子集** | 人工或更严过滤：去歧义、去过难环境、去争议实例 |
| **污染控制** | 训练数据仓与评测仓分离；可用「训练截止日后」的 issue |

### 2.4 SWE：如何扩覆盖而不稀释信号

| 手段 | 对覆盖的作用 |
|------|----------------|
| **扩展仓清单** | 新库/新生态进集；Multilingual 等换语言维度 |
| **时间窗 / 新 PR collect** | 新 issue 类型随项目演进进入样本 |
| **子集策略** | Full 偏广；Verified/Lite 偏深——扩广与提纯分开选 |
| **FAIL_TO_PASS 仍门禁** | 加仓时不能为凑数放宽执行验证，否则「假广」 |
| **元数据与分层报告** | 按 repo/领域报 resolve，避免一个总分掩盖空白格 |

### 2.5 SWE 侧「好实例」性质

| 性质 | 含义 |
|------|------|
| **真实性** | 真人提交并 merge 的工程问题，非合成小题 |
| **可验证** | 依赖仓库自带测试，而非 LLM judge |
| **非平凡** | 至少一个 FAIL_TO_PASS；不是改注释就过 |
| **环境可复现** | 给定 version 能稳定 install + test |
| **规模与定位难** | 大仓、多文件；考察检索与理解，不只单函数补全 |
| **持续可扩展** | 流水线可对新 PR 再生产，减数据泄露窗口 |
| **回归安全** | PASS_TO_PASS 防止「拆东墙补西墙」 |

衍生：SWE-bench Verified、Multimodal、Multilingual、SWE-smith（合成训练）等，都是在「同一哲学」上换过滤强度、模态或数据生产方式。

## 3. Terminal-Bench：如何做一个任务包

### 3.0 选题规则（写什么、拒什么）

```text
选题动机（人）
  → 真实世界有人愿付钱做的终端任务（系统、安全、数据、科学、工程……）
  → 能力面可以比 SWE 更杂，但仍是「CLI/容器里做成一件事」，不是办公套件场景

好选题信号
  ✓ 终态可程序化检查（文件/端口/协议/哈希/截图相似度等）
  ✓ 难在概念与推理，不在无意义磨时间
  ✓ 说明短而充分：知情工程师知道要什么，且与 verifier 对齐
  ✓ 有 Oracle 路径，数小时内可实现

差选题 / 应拒
  ✗ 只能靠 LLM 主观打分、终态说不清
  ✗ 步骤剧透型「按 1.2.3 敲命令」clerical 题
  ✗ Oracle 依赖隐藏文件/只有作者知道的trick
  ✗ 易 reward hack（改测试、读答案、空壳实现）
  ✗ 纯资源折磨（无概念增量的超长编译/随机网络）

入集路径
  投稿 → proposal rubric（可验证/无歧义/可解/真难/真实/评结果）
  → Oracle + tests 落地 → 多 Agent 试跑与轨迹审查 → 合入版本集
  → 发布后 Verified：修 timeout、资源、hack（如 2.0→2.1）
```

要点：**TB 选题是策展 + 对抗写作**，覆盖广来自 **领域多样 + 元数据分层 + 拒 homogeneity**；单题质量靠终态验证与反 hack，不是自动挖 PR。

### 3.1 任务目录（Harbor / TB 结构）

```text
<task-id>/
├── instruction.md      # Agent 可见说明（目标终态，少教步骤）
├── task.toml           # 元数据、超时、CPU/内存、网络、镜像等
├── environment/        # Dockerfile（+ 夹具）；勿塞入隐藏标准答案测试逻辑不当暴露
├── solution/solve.sh   # Oracle：证明可解
└── tests/
    ├── test.sh         # 安装依赖、跑断言、写 reward
    └── test_*.py       # 客观检查
```

Verifier 约定（关键）：`tests/test.sh` 必须在成功时写入 **`/logs/verifier/reward.txt`**（常见 `1`/`0`）；可附 CTRF 等结构化日志。需要「Agent 看不见的判分环境」时，用独立 verifier 镜像，并用 `artifacts` 从 Agent 容器导出产物。

### 3.2 构建 / 验收流水线（实践顺序）

```text
1. 选题：定 outcome 与领域，确认可程序化验证、概念难
2. 写清 outcome（instruction）——与 tests 对齐，不剧透步骤
3. 配 task.toml（timeout / resources / allow_internet / image）
4. 做 environment（依赖与夹具；默认不含 solution/tests 泄漏）
5. 写 Oracle solve.sh → 跑 oracle 必须稳定过（证明可解）
6. 写 tests：只验证文档化终态；显式防 reward hack
7. 多 Agent × 多 trial 试跑 + 人工看轨迹：过易 / 过歧义 / 可作弊则改
8. 合入版本集；日后 Verified 轮次修 timeout、资源、hack
```

TB 2.1 相对 2.0：大量任务因 **修 bug、调资源/超时、抗 reward hacking** 而修订——说明 **发布后仍要运营单题质量**；扩领域则靠新版本合入新投稿。

### 3.3 构建时必须盯住的模块

| 模块 | 注意点 |
|------|--------|
| **instruction.md** | 短、具体、终态导向；忌 AI 套话与逐步剧透 |
| **task.toml** | agent/verifier timeout、cpus/memory、`allow_internet`、镜像钉死 |
| **environment** | 可复现构建；网络策略明确；夹具完整 |
| **solution（Oracle）** | 不依赖「只有作者知道的隐藏文件」；deterministic |
| **tests / reward** | 测对的东西；防改测试、假实现、读到答案 |
| **artifacts（可选）** | 跨容器判分时导出清单要完整 |
| **元数据** | difficulty、category、expert_time；便于分层与分析 |
| **跑测协议** | 多 trial（官方常要求 ≥5）、并发、上传轨迹；看方差不只看均值 |

### 3.4 TB：如何用策展把「各个方面」放进集子

| 手段 | 对覆盖的作用 |
|------|----------------|
| **category / difficulty 元数据** | 报告与分析按格子看，而不是只看总分 |
| **proposal rubric 里的 Realistic** | 把题锚在真实工种，减少同一类 clerical 题堆叠 |
| **显式缺领域征稿** | 社区投稿天然偏热门栈；策展要补冷门但重要的终态类 |
| **instruction 短 + 终态多样** | 同一 verifier 模式可套不同领域 outcome |
| **版本集合稿** | 2.x 增删题时保持维度表：哪格仍空、哪格过密 |
| **拒「假广」** | Difficult 要概念难；纯磨资源/步骤剧透不算扩覆盖 |

### 3.5 TB 任务提案 Rubric（六条）

Terminal-Bench 接受任务时的硬筛选（提案评审常用）——**保证单题可测、可解**；与 **Coverage** 配合：六条过门后，还要看该题落在 taxonomy 哪格、是否补缺：

| # | 性质 | 要点 |
|---|------|------|
| 1 | **Verifiable** | 程序几乎总能抓住错、几乎总能承认对 |
| 2 | **Well-specified** | 说明写尽 verifier 会查的点；不靠猜 |
| 3 | **Solvable** | 有 Oracle 或强论证；知情者数小时内可实现 |
| 4 | **Difficult（好理由）** | 概念难，而非纯磨时间/堆资源/ clerical 步骤 |
| 5 | **Realistic / Interesting** | 真实世界有人愿付钱做的事 |
| 6 | **Outcome-verified** | 评终态不评「必须用 emacs」；防作弊除外 |

### 3.6 「好 TB 任务」三原则（写作指南）

来自任务作者/评审经验总结（[Guideline](https://arxiv.org/html/2604.28093)）：

| 原则 | 含义 |
|------|------|
| **Adversarial** | Benchmark ≠ Prompt；不要写成「哄模型成功」 |
| **Difficult** | 概念与推理难；优雅任务往往说明短、但要想清楚再动手 |
| **Legible** | 成本与基建可被社区复现；否则排行榜不可信 |

常见反模式（构建时逐条排查）：

- AI 生成、冗长、强调过头的 instruction  
- 过度规定步骤（clerical difficulty）  
- Oracle 依赖隐藏知识  
- Tests 测错对象 / 过宽 / 可 hack（据估计热门终端基准里可 hack 比例可观）  
- 环境困难冒充概念困难（无意义超长编译、纯资源折磨）

## 4. 并排：选题 + 模块 + 覆盖 checklist

构建或审查任一 Agent benchmark 时，先问 **要测哪些维度（taxonomy）**，再问选题与模块，再问格子是否铺满：

### 4.1 选题

| 问题 | SWE | TB |
|------|-----|-----|
| 题从哪来？ | 真实 Merged PR + Issue + 测试改动 | 人写终态任务 + rubric 收题 |
| 为何入选？ | 执行验证出 FAIL_TO_PASS | 可验证、无歧义、可解、概念难、抗 hack |
| 覆盖如何扩展？ | 加仓 / 加时间窗 / 加语言；按 repo 分层报分 | taxonomy + category；缺格征稿；策展平衡难度与成本 |
| 明确不选什么？ | 无测试预言机、装不起、无 fail→pass | 主观分、剧透步骤、易刷分、纯磨资源 |

### 4.2 模块

| 关注模块 | SWE 问法 | TB 问法 |
|----------|----------|---------|
| 任务陈述 | Issue 是否清楚、有无歧义？ | instruction 是否只描述终态且充分？ |
| 金标 | Gold patch 是否最小且正确？ | Oracle 是否稳定、无隐藏依赖？ |
| 验证器 | FAIL_TO_PASS / PASS_TO_PASS 是否公正？ | reward 是否难刷、与说明一致？ |
| 环境 | version install 是否钉死？ | 镜像/Dockerfile/资源/网络是否可复现？ |
| 隔离 | 测试是否泄漏解答？ | tests 是否在 Agent 视角下不可见或不可改判？ |
| 难度 | 是否需要仓级推理？ | 是否概念难而非 clerical？ |
| 污染 | 训练/评测是否隔离？ | 题面是否已大量出现在预训练语料？ |
| 统计 | 单次 resolve 率是否够？ | 多 trial、置信区间、轨迹审查？ |
| 维护 | 依赖腐烂怎么办？ | Verified 轮次修 hack / timeout？ |

### 4.3 覆盖门禁（扩题前先画格子）

- [ ] 已写 **能力/领域 taxonomy**（哪怕粗：修 bug / 运维 / 安全 / 数据 / 科学…）  
- [ ] 每格有 **最少题量或权重** 目标，避免总分被单一领域 dominate  
- [ ] 新题入集时标注 **category + difficulty**，可自动生成覆盖热力图  
- [ ] 扩 SWE：新仓是否带来 **新栈/新失败模式**，还是同质 Python 题 +1  
- [ ] 扩 TB：新投稿是 **补空格子** 还是重复热门模板  
- [ ] 报告分数时 **分层**（按 repo / category），不单给一个 leaderboard 数  
- [ ] 「广」与「深」子集分开说明（Full vs Verified；TB 版本说明侧重）

单题可靠、防 hack、可复现等见 §5，与覆盖分开勾选。

## 5. 设计时优先考虑的「性质」总表

无论走挖掘还是手写，优质 Agent 数据集通常要同时满足：

| 性质 | 说明 |
|------|------|
| **Validity（有效）** | 金标能过；无金标时任务仍可解 |
| **Reliability（可靠）** | 同环境重复跑，判分稳定 |
| **Discrimination（区分度）** | 强弱 Agent 分得开；别全体 0 或全体 1 |
| **Fairness / Spec clarity** | 说明与 verifier 对齐；无暗箱扣分 |
| **Anti-hacking** | 改测试、硬编码、读答案文件等路径被堵 |
| **Coverage / Breadth** | taxonomy 各维度有代表实例；报告宜分层而非仅总分 |
| **Representativeness** | 样本与所声称的目标场景分布一致 |
| **Ecological validity** | 接近真实工作（修 issue / 真终端任务） |
| **Reproducibility** | 镜像、种子、超时、依赖可钉死 |
| **Scalability / Freshness** | 能增产或换新题，减轻污染 |
| **Cost / Tractability** | 单题时长与算力可被社区承担 |
| **Safety & License** | 开源协议允许；无不当隐私/破坏性要求 |

SWE 侧重 **真实 PR 挖掘 + 测试预言机**，覆盖扩展依赖 **仓清单与时间窗**；TB 侧重 **人选题 + 容器终态验证**，覆盖扩展依赖 **taxonomy 与策展**。自建 benchmark 宜 **先固定维度表与选题规则，再以分层分数检验各维度是否遗漏**。

## 6. 读代码 / 读论文时的建议顺序

1. SWE：论文 §2 构建 + Appendix 执行验证；再看 `swebench/collect` 与 validation——重点看 **选仓/过滤条件**。  
2. TB：Harbor [Task Structure](https://www.harborframework.com/docs/tasks) + TB3 proposal rubric——重点看 **收题标准与拒题理由**。  
3. 写作观：[2604.28093](https://arxiv.org/html/2604.28093)——对抗性选题与反模式。  
4. 对照跑测：多 trial；失败归因 **环境 / 超时 / hack / 真能力**；据此改题而不是只改 Agent。

## 7. 小结

```text
选题：
  SWE = 挖「Merged + Issue + 测试改动」的 PR，再用 FAIL_TO_PASS 执行录取
  TB  = 人写「可验证终态 + 概念难 + 真实」的终端题，再用 rubric 录取

覆盖：
  taxonomy · 分层配额/策展 · category 元数据 · 分层报分 · 控制同质题堆叠

单题质量（§5）：
  钉环境 · 客观判分 · 金标/Oracle · 多 trial · 反 hack · 说明与 verifier 对齐

顺序：
  维度表与选题规则 → 扩覆盖 → 单题 reliability/防 hack 与覆盖设计并行
```
