# 04 — 状态、通道与控制流

## 状态模型

LangGraph 的节点通过**共享状态**通信：

```text
节点输入：当前 State（或子集）
节点输出：Partial[State]（只写需要更新的字段）
合并：按字段对应的 Channel / reducer 合并进全局状态
```

### Schema 常见写法

1. **TypedDict + Annotated reducer**（最常见）
2. **Pydantic / dataclass**（也支持，由内部字段解析转 channel）
3. **MessagesState / MessageGraph**（消息场景捷径，见 `graph/message.py`）

```python
from typing_extensions import Annotated, TypedDict
from langgraph.graph.message import add_messages


class AgentState(TypedDict):
    messages: Annotated[list, add_messages]
    step: int  # 默认 LastValue：后写覆盖
```

### context vs state

| | state | context |
|---|---|---|
| 可变性 | 节点可写 | 运行期只读上下文 |
| 典型内容 | messages、plan、tool results | user_id、db 连接、租户信息 |
| API | `state_schema` | `context_schema`（旧 `config_schema` 已弃用方向） |

## Channel 选型直觉

`StateGraph` 编译时会把 schema 字段映射为 channel。选择依据主要是「多个节点同时写这个 key 时怎么办」。

| 需求 | 倾向 |
|------|------|
| 标量 / 最新值 | `LastValue`（默认覆盖） |
| 列表追加 / 自定义合并 | `Annotated[..., reducer]` → binary op / 专用 reducer |
| 本步临时信号 | `EphemeralValue` |
| 多路汇聚再继续 | Barrier 类 channel |
| 增量 / 流式 delta | `DeltaChannel` 等 |

**原则**：状态设计先想清楚「谁写、写几次、如何合并」，再画边；很多 bug 来自缺少 reducer 却多节点同写。

## 边与分支

静态结构：

- `add_edge(a, b)` / `set_entry_point` / `set_finish_point`
- `add_conditional_edges`：根据状态选下一跳
- `START` / `END` 常量标记入口出口

动态结构：

### `Send` — 扇出

运行期决定「给节点 X 发一份自定义输入」，常用于 map-reduce：一个规划节点拆出 N 个子任务，各自 `Send("worker", payload)`。

### `Command` — 更新 + 路由

在一次节点返回里同时：

- 更新部分状态
- 指定 `goto` 下一节点（或列表）
- 甚至带上图控制语义

适合「工具结果决定跳转」而不想拆成「写状态节点 + 条件边」两段。

## 子图（Subgraph）

图可以嵌套：子图本身是编译后的 runnable，作为父图的一个节点。用于：

- 模块化（检索子图、编码子图）
- 独立 checkpointer 命名空间
- 复用同一段流程

`examples/subgraph.ipynb` 等示例可对照。

## 消息路径特写

`add_messages` / `MessagesState` 专门处理对话消息：

- 追加新消息
- 按 message id 更新 / 删除（实现细节见 `graph/message.py`）
- 与 streaming messages 模式配合

多数 Chat Agent 的 state 核心就是 `messages` 一个字段 + 少量控制字段。

## 最小控制流对照

| 模式 | 做法 |
|------|------|
| 线性流水线 | `A → B → C → END` |
| 条件分支 | `add_conditional_edges` |
| 循环（ReAct） | agent ⇄ tools，条件到 END |
| 扇出聚合 | `Send` + reducer / barrier |
| 人工卡点 | 节点内 `interrupt`，resume 继续 |
| 动态跳转 | 返回 `Command(goto=...)` |

## 实践建议

1. **State 尽量小**：只放恢复与路由真正需要的字段；大对象放 Store / 外部存储，state 留引用。
2. **每个会并发写的字段都要有明确 reducer**。
3. **先静态图画通，再引入 Send/Command**；动态拓扑难调试。
4. **input/output schema 与内部 state 分离**：对外 API 稳定，对内可演进。
