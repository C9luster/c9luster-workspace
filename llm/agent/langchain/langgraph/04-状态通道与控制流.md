# 04 — 状态、通道与控制流

## 状态模型

LangGraph 的节点通过**共享状态**通信：

```text
节点输入：当前 State（或子集）
节点输出：Partial[State]（只写需要更新的字段）
合并：按字段对应的 Channel / reducer 合并进全局状态
```

### Schema 常见写法

1. **TypedDict + Annotated reducer**（最常见）
2. **Pydantic / dataclass**（也支持，由内部字段解析转 channel）
3. **MessagesState / MessageGraph**（消息场景捷径，见 `graph/message.py`）

```python
from typing_extensions import Annotated, TypedDict
from langgraph.graph.message import add_messages


class AgentState(TypedDict):
    messages: Annotated[list, add_messages]
    step: int  # 默认 LastValue：后写覆盖
```

### context vs state

| | state | context |
|---|---|---|
| 可变性 | 节点可写 | 运行期只读上下文 |
| 典型内容 | messages、plan、tool results | user_id、db 连接、租户信息 |
| API | `state_schema` | `context_schema`（旧 `config_schema` 已弃用方向） |

## Channel 选型直觉

`StateGraph` 编译时会把 schema 字段映射为 channel。选择依据主要是「多个节点同时写这个 key 时怎么办」。

| 需求 | 倾向 |
|------|------|
| 标量 / 最新值 | `LastValue`（默认覆盖） |
| 列表追加 / 自定义合并 | `Annotated[..., reducer]` → binary op / 专用 reducer |
| 本步临时信号 | `EphemeralValue` |
| 多路汇聚再继续 | Barrier 类 channel |
| 增量 / 流式 delta | `DeltaChannel` 等 |

**原则**：状态设计先想清楚「谁写、写几次、如何合并」，再画边；很多 bug 来自缺少 reducer 却多节点同写。

## Node / Edge：棋盘隐喻（控制流内核）

可以把一次运行想成**回合制棋**：

| 概念 | 隐喻 |
|------|------|
| State | 棋盘局面 |
| Node | 允许行动的格子 |
| Edge | 合法走法：谁行动完后下一回合点名谁 |
| Superstep | 一回合 |

### Node：能干什么

```text
读 State → 计算 → 返回 Partial[State]（或 Command）
```

- **不会自己醒来**：必须有人写入触发信道 `branch:to:{节点名}`
- **不直接调用下一个 node**：通过边 / `Command` / `Send` 交棒
- 返回值经 channel/reducer 合进局面

### Edge：合法走法

| API | 含义 |
|-----|------|
| `add_edge(A, B)` | A 结束后点名 B |
| `add_edge([A, B], C)` | A、B **都到齐**再点名 C（barrier） |
| `add_conditional_edges(A, path)` | A 结束后由 `path(state)` 决定下家（可多目标 / `END` / `Send`） |
| `START` / `END` | 入口点名 / 终局（END 不是业务节点） |

编译后固定边 ≈：节点写完后往 `branch:to:B` 写一笔。  
**边不搬运业务参数**；下一节点读的仍是合并后的全局 State。

### 一回合实际顺序

```text
① 本回合谁被点名（哪些 branch:to:* 有信号）
② 这些 node 并行执行
③ Partial[State] 按 channel/reducer 合盘
④ 按边 / Command / Send 写下回合点名
⑤ checkpoint（若有）
⑥ 点到 END 或无人可点 → 终局
```

### `Send` / `Command`：动态改走法

| 手段 | 含义 |
|------|------|
| `Send(node, arg)` | 动态扇出，可带自定义输入（map-reduce） |
| `Command(update=..., goto=...)` | 更新状态的同时指定下家 |

二者最终仍落到写 `branch:to:*` 或投递任务，与静态边同一套唤醒机制。

### 限制一览

| 想限制的事 | 靠什么 |
|------------|--------|
| 谁能跑 | 有没有写到 `branch:to:该节点` |
| 跑完去哪 | 边 / 条件边 / `Command.goto` |
| 状态怎么改 | node 返回值 + reducer（与边无关） |
| 何时停 | `END` 或条件边返回结束 |

**一句话：node 改棋盘；edge 定下一手轮到谁。**

## 边与分支（API 速览）

静态结构：

- `add_edge` / `set_entry_point` / `set_finish_point`
- `add_conditional_edges`
- `START` / `END`

动态结构：见上文 `Send` / `Command`。

## 子图（Subgraph）

图可以嵌套：子图本身是编译后的 runnable，作为父图的一个节点。用于模块化、独立 checkpointer 命名空间、复用流程。

## 消息路径特写

`add_messages` / `MessagesState` 处理对话消息追加与按 id 更新。多数 Chat Agent 的 state 核心就是 `messages` + 少量控制字段。

## 最小控制流对照

| 模式 | 做法 |
|------|------|
| 线性流水线 | `A → B → C → END` |
| 条件分支 | `add_conditional_edges` |
| 循环（ReAct） | agent ⇄ tools，无 tool_calls → END |
| 扇出聚合 | `Send` + reducer / barrier |
| 人工卡点 | 节点内 `interrupt`，resume 继续 |
| 动态跳转 | 返回 `Command(goto=...)` |

## 实践建议

1. **State 尽量小**：只放恢复与路由真正需要的字段。
2. **并发写的字段都要有明确 reducer**。
3. **先静态图画通，再引入 Send/Command**。
4. **input/output schema 与内部 state 分离**。
