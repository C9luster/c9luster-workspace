# 08 — 心智模型与常见误解

本文沉淀讨论中反复澄清的结论，建议在读完 01 / 04 / 05 后阅读。

---

## 1. 最终定论：给什么、不给什么

| LangGraph 给什么 | 默认不替你定什么 |
|------------------|------------------|
| 图运行时（节点/边/State/Pregel） | 业务 Agent「怎么想」 |
| ReAct 循环的**驱动与约束** | memory / 上下文**策略**细节 |
| Checkpoint / Store **管道与接口** | 如何拼 system prompt、何时摘要 |
| HITL、流式、重试等基础设施 | 工具业务语义、权限产品策略 |

> **模块化 Agent 工具 + 耐久跑道；细节策略要自己实现（或用上层 harness 的默认再改）。**

上下文管理同理：核心层**要自己做**；`create_agent` middleware / Deep Agents 只提供半成品或更厚默认栈。

---

## 2. 「看起来都是 workflow」——对，这是刻意的

LangGraph 底盘就是 **durable workflow（状态图）**。  
所谓 Agent，多半是「带 LLM 决策边的 workflow」，例如：

```text
agent ──有 tool_calls──► tools ──► agent ...
   └──无 tool_calls──► END
```

| | 偏 workflow | 偏 agentic |
|---|---|---|
| 下一跳谁定 | 人写死 / 规则 | LLM 输出驱动条件边 |
| 路径形态 | 静态、可审计 | 循环、长度不定、可 `Send` |
| 引擎 | 同一套 `StateGraph` | 同一套 `StateGraph` |

不是「把 Agent 做成了 workflow」，而是：**Agent = 特殊形态的 durable workflow。**  
体感像工作流，是因为循环被**摊开成边**（方便 HITL、恢复、混确定性步骤）。

---

## 3. 编排 vs 调度：为何「人工画图」仍适合 Agentic

| 层 | 谁定 | 例子 |
|----|------|------|
| **编排（棋规）** | 人 | 有哪些节点、能否调工具、何时结束、要否审批 |
| **调度（每一步）** | LLM（或规则） | 本步调不调工具、调哪个、是否继续 |

人编排的是**合法走法**；不是每一步「下一步去哪」都由人写死。

```text
人：定棋规。LLM：在棋规里下棋。
LangGraph = 棋规引擎，不是替 LLM 下每一步。
```

「调度全由 LLM」在工程上从不等于零约束：工具真执行、失败恢复、安全中断、死循环上限，都必须有人设 runtime。LangGraph 适合的正是这一层。

完全无预定义节点、模型现场发明任意控制流且可生产恢复——**任何可靠系统都做不到**；不是 LangGraph 独有短板。

---

## 4. ReAct：脑在 LLM，腿与安全带在 LangGraph

```text
LangGraph（或 create_agent / Deep Agents）
  └── 驱动循环：调模型 → 看 tool_calls → 跑工具 → 再调模型 → …
        ├── LLM：推理、是否/调用哪个工具
        ├── 图/边：无 tool_calls 则结束等规则
        ├── checkpoint / interrupt：恢复、人工卡点
        └── callback / middleware：旁路 hook
```

| 谁 | 干什么 |
|----|--------|
| LLM | ReAct 的「脑」 |
| LangGraph | ReAct 的「腿 + 安全带」 |

不是「LLM 自己转圈，LangGraph 只挂 hook」；**循环本身**由 runtime/harness 驱动。

---

## 5. 和自研框架的同构类比

LangGraph 条件边很大一块，就是显式化：

> **LLM 返回长什么样 → 下一步允许干什么**

例如：

| LangGraph | 自研常见写法 |
|-----------|--------------|
| 无 `tool_calls` → `END` | tool_call 为空则 finish |
| 有 `tool_calls` → `tools` 节点 | 走工具执行再回模型 |
| 节点输出 / 流式事件 | 产出 Event |
| 主循环路由 | 「何种结果则下一步」 |
| callback / middleware | Event → Hook（**旁路副作用**） |

注意拆开：

- **主循环路由** ≈ 条件边 / Command  
- **Event→Hook** 很多是观测、入库、沙箱副作用，**不等于**下一跳节点  

`MiaodaRuntime` / `CLIRuntime` 更像**工具执行面 / sandbox**，不是 Pregel 调度器。  
Session 产品能力 ≈ `thread_id` 容器 + Event 账本 + Runtime 绑定；**Checkpoint 只是其中「可恢复状态」那一块**。

## 6. Memory / 上下文：管道 vs 策略

| | 管道（框架给） | 策略（默认自管） |
|---|---|---|
| 短期 | Checkpoint 保住 State | 哪些字段进 prompt、如何裁剪 |
| 长期 | Store KV（可选向量） | 存什么、何时检索、如何注入 system prompt |
| 上下文 | messages 可无限累积 | 滑窗 / 摘要 / 外置大结果 |

`InMemoryStore` **只是一种 Store 实现**；默认 KV，向量检索可选。

详见 [05-持久化与关键能力](./05-持久化与关键能力.md)。

## 7. 误解速查

| 误解 | 更正 |
|------|------|
| LangGraph 不适合 Agentic | 适合做 **Agentic 的 runtime**；不适合当零心智玩具 API |
| 全是人工编排 = 每步人调度 | 人设棋规；步级调度常跟 LLM 输出 |
| 不依赖 LangChain 了 | 可不装完整 `langchain`；仍依赖 `langchain-core`；Agent 工厂在往 `create_agent` 收 |
| Checkpoint = 完整 session | ≈ session 内可恢复状态；session 产品通常更宽 |
| Store = 向量库且自动进 prompt | 通用 KV（可选向量）；注入 prompt 要自己写 |
| 上下文框架会自动管好 | 核心层不管；要自建或用 harness/middleware |
| LangGraph 只挂 hook | 它驱动 ReAct 循环本身 + 兜底能力 |

---

## 8. 一句话墙

```text
LangGraph = durable workflow runtime（Agent 是其上的一种图形态）
人定棋规，LLM 在规内 ReAct；框架跑循环、做恢复与 HITL
Memory/上下文/Prompt = 管道有了，策略你写（或用上层默认再改）
和自研「tool_call 空则结束 / Event 分发」同构；Runtime ≠ 图调度器
```
