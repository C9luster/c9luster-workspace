# 05 — 持久化与 Memory

LangGraph 的「记忆」不是一个万能 Memory 类，而是 **Checkpoint（短）+ Store（长）+ 你自己的策略层**。本章按机制拆开讲。

---

## 0. 分层总览

```text
┌─────────────────────────────────────────────────────────┐
│ 策略层（默认自建 / 可选 middleware）                        │
│  滑窗 · 摘要 · 工具结果卸载 · 检索后注入 prompt               │
└─────────────────────────────────────────────────────────┘
            │ 读写
┌───────────┴────────────┬────────────────────────────────┐
│ 短期：Checkpointer      │ 长期：Store                      │
│  按 thread 存图状态     │  跨 thread 的 namespace KV         │
│  自动续跑 / HITL / 恢复 │  显式 put/get/search；可选向量   │
└────────────────────────┴────────────────────────────────┘
```

| | Checkpoint | Store |
|---|---|---|
| 典型问题 | 「这场对话/任务跑到哪了？」 | 「跨会话要记住什么？」 |
| 作用域 | 单个 `thread_id`（可含子图 `checkpoint_ns`） | 任意 namespace，常跨 thread |
| 写入方式 | 运行时按 superstep **自动**落盘 | 节点里 **显式** `put` |
| 读出方式 | 同 thread 再次 `invoke` **自动**加载 | 节点里 `get` / `search` |
| 和 prompt | 常含 `messages`，由节点决定如何送模型 | **不会**自动进 prompt |
| 实现举例 | `InMemorySaver`、Postgres、SQLite | `InMemoryStore`、Postgres Store 等 |

## 1. Checkpoint：短期记忆与耐久执行

### 1.1 它是什么

**Checkpoint** = 某一时刻图状态的快照。  
**CheckpointTuple** = `(config, checkpoint, metadata, parent_config, pending_writes)`。

路径：`libs/checkpoint/`（接口）+ `checkpoint-postgres` / `checkpoint-sqlite`（后端）。

它保存的是 **可恢复的运行时局面**，通常包括：

- 各 channel 的当前值（如 `messages`、业务字段）
- 各 channel 的版本号（用于判断谁该被再次调度）
- 节点已见过的版本（`versions_seen`）
- 元数据（来源、step、父检查点等）
- 可选：pending writes（同一步未完成时的中间写）

**不是**专门的「对话日志服务」；对话轨迹往往以 `messages` 等形式住在 checkpoint 的 `channel_values` 里。

### 1.2 结构（概念字段）

`Checkpoint` 核心字段（见 `langgraph.checkpoint.base.Checkpoint`）：

| 字段 | 含义 |
|------|------|
| `v` | 检查点格式版本 |
| `id` | 检查点 ID（唯一且单调递增，可排序） |
| `ts` | ISO8601 时间戳 |
| `channel_values` | channel 名 → 反序列化后的值 |
| `channel_versions` | channel 名 → 单调递增版本 |
| `versions_seen` | 节点 →（channel → 已见版本）；决定下一步跑谁 |
| `updated_channels` | 本检查点更新过的 channel 列表（可选） |

`CheckpointMetadata` 常见：

| 字段 | 含义 |
|------|------|
| `source` | `input` / `loop` / `update` / `fork` |
| `step` | 步号；input 常为 `-1`，首个 loop 为 `0` |
| `parents` | 命名空间 → 父 checkpoint id（子图相关） |
| `run_id` | 产生该检查点的 run |

### 1.3 Thread 与配置

使用 checkpointer 时，调用必须带：

```python
config = {"configurable": {"thread_id": "user-42-session-1"}}
```

| 配置键 | 是否必需 | 含义 |
|--------|----------|------|
| `thread_id` | 是 | 一条检查点链的隔离 ID（多租户/多会话） |
| `checkpoint_id` | 否 | 指定从哪个快照续跑 / 读取 |
| `checkpoint_ns` | 否 | 命名空间；子图常用，根图多为 `""` |

```python
from langgraph.checkpoint.memory import InMemorySaver

graph = builder.compile(checkpointer=InMemorySaver())

# 第一轮
graph.invoke(
    {"messages": [{"role": "user", "content": "我叫小明"}]},
    config={"configurable": {"thread_id": "t1"}},
)

# 同 thread：自动带上上一轮状态（含 messages）
graph.invoke(
    {"messages": [{"role": "user", "content": "我叫什么？"}]},
    config={"configurable": {"thread_id": "t1"}},
)

# 从历史某点续跑 / 分支
graph.invoke(
    ...,
    config={
        "configurable": {
            "thread_id": "t1",
            "checkpoint_id": "1ef4f797-8335-6428-8001-8a1503f9b875",
        }
    },
)
```

### 1.4 何时写入

典型节奏（概念上）：

```text
input → 写 input 检查点
loop 每完成一个 superstep → 写 loop 检查点
手动 update_state / fork → 写 update / fork 检查点
interrupt 暂停前 → 状态已可恢复
```

因此短期「多轮记忆」的本质是：**同一 `thread_id` 下不断叠加的 State 快照链**。

### 1.5 Pending writes

同一步多个节点并行时，若其中一个失败：

- 已成功节点的写可作为 **pending writes** 关联到该检查点
- resume 时不必重跑已成功节点

对贵、有副作用的工具节点特别重要。

### 1.6 Checkpointer 接口

实现需符合 `BaseCheckpointSaver`，核心方法：

| 方法 | 作用 |
|------|------|
| `put` / `aput` | 存检查点 + metadata |
| `put_writes` / `aput_writes` | 存 pending writes |
| `get_tuple` / `aget_tuple` | 按 config 取一条 CheckpointTuple |
| `list` / `alist` | 按 thread 等条件列出历史 |
| `delete_thread` / `adelete_thread` | 删除该 thread 全部数据 |
| `get_next_version` | 生成下一 channel 版本号 |

异步图（`ainvoke` / `astream`）需要异步方法实现。

### 1.7 常见实现

| 实现 | 特点 |
|------|------|
| `InMemorySaver` | 进程内；开发 / 测试；进程退出即丢 |
| `SqliteSaver` / 异步变体 | 单机文件持久化 |
| `PostgresSaver` / 异步变体 | 生产常见；多进程/多副本共享 |

`compile(checkpointer=...)` 只依赖接口，换实现即可。

### 1.8 Agent 侧能力清单

有了 Checkpoint，Agent 层通常能做：

| 能力 | 说明 |
|------|------|
| 会话内短期记忆 | 同 thread 多轮 `messages` 等字段延续 |
| 耐久执行 | 崩溃、超时后按检查点续跑 |
| HITL | `interrupt` → 人审 → resume |
| 时光旅行 | 指定 `checkpoint_id` 回退/重跑 |
| 失败局部重试 | pending writes |
| 多租户隔离 | 不同 `thread_id` |
| 审计/调试基座 | `list` 历史检查点 + LangSmith 轨迹 |
| 清理 | `delete_thread` |

### 1.9 Serde 与安全

默认 `JsonPlusSerializer` 能序列化大量类型。  
**安全注意：** 默认反序列化面较宽。新应用建议：

- 环境变量 `LANGGRAPH_STRICT_MSGPACK=true`，或
- 显式传入 `allowed_msgpack_modules`

只把**恢复与路由真正需要**的数据放进 State；大文件、密钥、可外置对象不要塞进 checkpoint。

### 1.10 和「拼 LLM 请求」的关系

```text
Checkpoint 加载 → 得到 State（含 messages 等）
        → 节点 / prompt 逻辑决定送模型哪些内容
        → 模型返回 → 写回 State → 再 checkpoint
```

框架保证 **状态 Continuity**；**如何裁剪 messages、如何组 system prompt** 仍是策略层。

## 2. Store：长期记忆

### 2.1 它是什么

`BaseStore`：跨 thread 的持久 KV，支持层级 **namespace**，可选 **TTL** 与 **向量检索**。

路径：`libs/checkpoint/langgraph/store/`。

与 Checkpoint 的关键差别：**不会在每个 superstep 自动写入**；必须在节点（或外部代码）里主动 `put` / `get` / `search`。

### 2.2 数据模型

| 概念 | 说明 |
|------|------|
| `namespace` | `tuple[str, ...]`，如 `("users", "u123")`、`("docs",)` |
| `key` | 命名空间内唯一键 |
| `value` | **`dict[str, Any]`**（可过滤的字段） |
| `Item` | value + key + namespace + created_at / updated_at |

设计建议：用 namespace 划分租户、用户、文档集合；用 value 里的字段做业务过滤。

### 2.3 核心 API

| 方法 | 作用 |
|------|------|
| `put(namespace, key, value, index=..., ttl=...)` | 写入/更新 |
| `get(namespace, key)` | 精确读取 |
| `search(namespace_prefix, query=..., filter=..., limit=..., offset=...)` | 前缀下检索 |
| `list_namespaces(...)` | 列出命名空间 |
| `aput` / `aget` / `asearch` | 异步版本 |
| `batch` | 批量执行一组 Op |

`search` 行为：

- **无向量 index**：可按 `filter`、前缀做 KV 侧过滤/分页（实现相关）
- **有向量 index**：`query=` 走语义相似度；可与 `filter` 组合

`put(..., index=False)` 可跳过对该条的向量索引；`index=["text"]` 可指定要嵌入的字段（默认常为整份 value）。

### 2.4 InMemoryStore：一种实现，不是唯一定义

```python
from langgraph.store.memory import InMemoryStore

# ① 默认：纯内存字典 KV，无向量
store = InMemoryStore()
store.put(("users", "123"), "profile", {"name": "小明", "style": "简洁"})
item = store.get(("users", "123"), "profile")

# ② 可选：构造时传入 index，才启用语义搜索
store = InMemoryStore(
    index={
        "dims": 1536,
        "embed": embed_fn,       # 可调用列表 texts → vectors，或 Embeddings
        # "fields": ["text"],    # 可选：指定嵌入哪些字段
    }
)
store.put(("docs",), "d1", {"text": "Python tutorial", "type": "guide"})
hits = store.search(("docs",), query="python programming", filter={"type": "guide"})
```

要点：

- **Semantic search 默认关闭**；不配 `index` 就是普通 KV
- 数据在进程内存，退出即丢；持久化请用 DB 版 Store（如 Postgres）
- `compile(store=store)` 后，节点可通过参数 `store` 或 `get_store()` 访问

### 2.5 在图中的典型用法

```python
def remember(state, *, store):
    user_id = ...  # 来自 context / config
    store.put(("users", user_id), "prefs", {"tone": "正式"})
    return {}

def recall_and_prompt(state, *, store):
    item = store.get(("users", user_id), "prefs")
    style = (item.value if item else {}).get("tone", "默认")
    # 自行拼进 system / 额外 message —— 框架不会自动做
    return {"messages": [SystemMessage(content=f"用户偏好语气：{style}")]}

graph = builder.compile(checkpointer=checkpointer, store=store)
```

长期记忆进模型的路径永远是：**Store → 你的节点逻辑 → prompt / messages**。

### 2.6 适合存什么 / 不适合存什么

| 适合 | 不适合（或慎用） |
|------|------------------|
| 用户画像、偏好、长期事实 | 当前 turn 的完整 messages（应在 Checkpoint/State） |
| 可检索知识片段、笔记 | 超大二进制（更宜对象存储，Store 留引用） |
| 跨会话工具产物摘要 | 密钥、临时 token |

## 3. 短期 vs 长期：协作方式

```text
同一次对话（同一 thread_id）
  └─ Checkpoint 自动延续 State.messages / 中间字段

跨天、跨会话仍要记得的用户事实
  └─ 某节点 Store.put；下次任意 thread 里 Store.get/search 再注入

上下文太长
  └─ 策略节点：摘要写回 State 或 Store；原细节外置；再 checkpoint
```

实用口诀：

| 问题 | 答案 |
|------|------|
| 聊得续上吗？ | checkpointer + `thread_id` + State |
| 隔天还认识用户吗？ | Store 显式读写 |
| 上下文爆了吗？ | 自建策略（或 middleware / Deep Agents） |

## 4. 上下文管理策略（框架不内置完整方案）

LangGraph **核心**只保证 State 可存可续；**不会**自动：

- 滑窗截断  
- 超长摘要  
- 工具结果压缩  
- 按相关性召回历史  

### 4.1 常见自建模式

| 模式 | 做法 |
|------|------|
| 滑窗 | 节点里只保留最近 N 条 messages 再调模型 |
| 摘要 | 超过阈值 → LLM 摘要 → 写回 State（或 Store）替换长历史 |
| 结果卸载 | 大工具输出存 Store/文件，messages 只留引用或短摘要 |
| 检索增强 | 按当前问题 `store.search`，把 hit 注入 system/user |
| 分层 | 热数据在 State；温数据在 Store；冷数据在外部仓 |

### 4.2 上层可选用的半成品

| 层 | 能力 |
|----|------|
| `create_agent` + middleware | 可挂 summarization 等 |
| Deep Agents | 更厚默认（摘要、文件卸载等），仍可替换 |

无论哪一层，**业务阈值、保留字段、注入格式**仍需按产品调。

## 5. Human-in-the-loop 与持久化

```text
节点 interrupt → 当前状态已进入 checkpoint
→ 进程可退出
→ 之后用同一 thread_id（+ 可选 resume 值）继续
```

没有 checkpointer，HITL 很难做到真正的「停得住、回得来」。

---

## 6. Streaming / 可靠性（与持久化相邻）

- `stream` / `astream`：节点与消息级事件（偏可观测，不等于 Store）  
- 节点级：`RetryPolicy` / `CachePolicy` / `TimeoutPolicy`  
- Cache 另有 `BaseCache` 实现（内存 / Redis 等），与 Checkpoint/Store 不同职责：偏「同输入跳过重算」

## 7. 生产检查清单

**Checkpoint**

- [ ] 生产后端（Postgres 等），而非长期依赖 `InMemorySaver`
- [ ] 所有会话使用稳定、可路由的 `thread_id`
- [ ] HITL / 长任务验证 resume
- [ ] 收紧 serde；State 最小化
- [ ] 需要时暴露 `list` / 指定 `checkpoint_id` 的运维能力
- [ ] 注销策略：`delete_thread` 或 TTL/归档方案

**Store**

- [ ] 明确 namespace 规范（租户/用户/类型）
- [ ] 需要语义检索时再配 `index`；否则保持 KV
- [ ] 注入 prompt 的节点路径有测试
- [ ] 持久化实现与备份；内存版仅限开发

**策略**

- [ ] 上下文上限与摘要/滑窗策略落地
- [ ] 大对象外置，checkpoint/store 只留引用
- [ ] 超时、重试与关键工具节点对齐
