# 05 — 持久化、Memory 与关键能力

## Memory 总览（两层 + 策略自管）

LangGraph **没有**单一魔法 Memory 类包打天下：

```text
① 短期记忆（会话内）  → Checkpointer + thread_id + State（常含 messages）
② 长期记忆（跨会话）  → Store（namespace + KV，可选向量检索）
③ 上下文管理策略       → 默认要自己实现（或挂上层 middleware）
```

---

## Checkpoint：短期记忆与耐久执行

路径：`libs/checkpoint/` + `checkpoint-postgres` / `checkpoint-sqlite`

**Checkpoint** = 某一时刻**图状态**快照（不只是「对话 transcript」）。  
常含 `messages`，也可能含 step、flags、中间结果。  
主职是 **可恢复运行时状态**；其中字段再被你拿去拼 LLM 请求。

**CheckpointTuple** = checkpoint + config + metadata + pending writes。

### Thread

多租户 / 多会话靠 `thread_id` 隔离：

```python
config = {"configurable": {"thread_id": "1"}}
# 可选：从某一检查点续跑
config = {
    "configurable": {
        "thread_id": "1",
        "checkpoint_id": "0c62ca34-...",
    }
}
```

### Agent 层面一般支撑的能力

| 能力 | 含义 |
|------|------|
| 会话内记忆 | 同 thread 多轮，messages / 中间状态接着用 |
| 耐久执行 | 挂了、报错后从检查点续跑 |
| HITL | interrupt 暂停 → 人改/批 → resume |
| 时光旅行 | 指定 `checkpoint_id` 回退 / 重跑 |
| 失败局部重试 | pending writes：同一步成功节点不必重跑 |
| 多租户隔离 | 不同 `thread_id` |
| 线程清理 | `delete_thread` |

### 与「对话轨迹」的关系

- ✅ 可以当作会话轨迹的**载体**（尤其 `messages`）
- ❌ 不是专门的 prompt 编译器；怎么译成 LLM 请求仍是节点逻辑

### Pending writes / Serde

同一步多节点时，失败节点之外的成功写可保留。  
新应用建议收紧反序列化（如 `LANGGRAPH_STRICT_MSGPACK=true`）。

开发用 `InMemorySaver`；生产用 Postgres / SQLite checkpointer。

## Store：长期记忆（接口；实现可换）

**Store** = 跨 thread 的 KV，带层级 `namespace`；**可选** embedding 搜索。

```python
from langgraph.store.memory import InMemoryStore

# 默认：纯内存 KV，无向量
store = InMemoryStore()
store.put(("users", "123"), "prefs", {"style": "简洁"})
item = store.get(("users", "123"), "prefs")

# 可选：构造时配 index 才启用语义检索
store = InMemoryStore(index={"dims": 1536, "embed": embed_fn})
store.search(("docs",), query="...")
```

要点：

| 问题 | 答案 |
|------|------|
| `InMemoryStore` 是不是唯一 Store？ | 否，只是一种实现；还有 Postgres 等，也可自实现 `BaseStore` |
| 是不是只能做向量检索？ | 否；**默认是 KV**，向量是 `index=` 可选能力 |
| 会不会自动进 system prompt？ | **不会**；节点里 `get`/`search` 后自己拼 prompt |
| 能存用户风格吗？ | 能；完全自定义 value 与用法 |

| | Checkpoint | Store |
|---|---|---|
| 作用域 | 单个 `thread_id` | 跨 thread（用 namespace 划分） |
| 存什么 | 整图 State | 你显式 put 的文档 / 画像 |
| 怎么用 | 同 thread 自动续上 | 节点里读写，手动注入 |

## 上下文管理策略：核心层要自己做

LangGraph 本体：

- 负责把 State（常含完整 `messages`）存进 checkpoint
- **不会**自动摘要、滑窗、裁剪、离线归档
- 上下文爆 token 是业务侧问题

可选加速：

| 层 | 上下文能力 |
|----|------------|
| LangGraph 核心 | 管道 only → **策略自实现** |
| `create_agent` + middleware | 可挂 summarization 等半成品 |
| Deep Agents | 更厚的默认栈（摘要、文件卸载等），仍可替换 |

常见自建策略：滑窗、超阈值摘要写回 State/Store、大工具结果落外存只留引用、按需从 Store 检索注入。

## Checkpoint vs 产品 Session（对照）

| 概念 | 更像什么 |
|------|----------|
| 产品 `session_id` / conversation | LangGraph **`thread_id`**（隔离键） |
| Checkpoint | session 内**可恢复运行时快照** |
| 完整 session 能力 | 通常更宽：事件账本、沙箱绑定、生命周期、UI 回放 |

```text
Session（产品）
├── session_id           ≈ thread_id
├── Event 账本 / 回放    ≈ transcript（不完全是 checkpoint）
├── Runtime/Sandbox 绑定 ≈ 执行环境（checkpoint 不管）
└── 可恢复 Agent 状态    ≈ checkpoint 本职
```

Event 入库与 Checkpoint 常一起用：Event 给展示/审计，Checkpoint 给「接着干」。

## Human-in-the-loop

执行到需人工处 → `interrupt` → 状态已 checkpoint → 审阅/修改 → resume。  
没有 checkpointer，HITL 的「停得住、回得来」会大打折扣。

## Streaming / 可靠性策略

- `stream` / `astream`：节点与消息级事件
- 节点级：`RetryPolicy` / `CachePolicy` / `TimeoutPolicy` / error_handler

## 生产检查清单

- [ ] checkpointer 后端（Postgres 常见）
- [ ] 稳定 `thread_id`
- [ ] HITL / 长任务可 resume
- [ ] 收紧 checkpoint serde
- [ ] 大对象不进 state；长期事实走 Store 或外存
- [ ] **上下文策略**显式落地（摘要/滑窗/卸载）
- [ ] 关键流式事件与超时重试
