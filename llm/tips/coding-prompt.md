# 写好 Coding Prompt

## 一句话

好 prompt 不是写得更长，而是把任务做成 **可验收的小闭环**：目标清楚、边界清楚、怎么验清楚。

## 五块结构（缺一块就容易跑偏）

| 块 | 要写清的事 | 不问会怎样 |
|----|------------|------------|
| **完成态** | 做完后系统长什么样，用户能干什么 | Agent 自行发明需求 |
| **范围** | 改哪些文件/模块，明确不要动什么 | 顺手重构、扩 scope |
| **约束** | 语言、框架、现有模式、兼容性 | 另起一套「最佳实践」 |
| **上下文** | `@` 关键文件、接口、错误日志 | 猜架构，改错层 |
| **验收** | 测什么、跑什么命令、什么算失败 | 「看起来对」就停 |

## 可直接套的模板

```text
目标：实现 X，让 Y 场景能 Z。
不要：改无关模块、重构、加新抽象。
约束：沿用现有模式（指出文件），公共 API 不变。
上下文：相关文件 / 接口 / 失败日志如下。
验收：
- [ ] 行为 A
- [ ] 命令 B 通过
- [ ] 不出现副作用 C
先给 3 步计划，等我确认再改代码。
```

Cursor / Claude Code 里把设计稿、类型定义、失败测试一起 `@` 进去，比口头描述架构更准。

## 三条实操规则

1. **一次一事**：一次 prompt 只做一个可 review 的 diff。大需求拆成「调研 / 方案 / 实现 / 修测试」。
2. **把决策写死**：已经选好的方案要说清楚，否则 Agent 会重新设计。
3. **用测试当合同**：失败用例、期望行为、复现命令，比形容词稳。

长期有效的不是单条神 prompt，而是仓库记忆：`AGENTS.md`、`.cursor/rules`、skills。把「怎么写代码、怎么测、禁止做什么」固化下来，每次会话才不用从头教。

## 反例

| 差写法 | 为什么差 |
|--------|----------|
| 「帮我优化一下」 | 没有完成态，也没有验收 |
| 「按最佳实践重构」 | 默认授权扩 scope |
| 一次丢 10 个需求 | 上下文互相污染，diff 无法收口 |
| 整仓倾倒、不标入口 | 注意力被噪声占满 |

## 和「应用 Prompt」的差别

调模型做问答时，prompt 主要管语气和格式。Coding Agent 的 prompt 还要管 **工具怎么用、改哪里、改完怎么证伪**。后者失败，多半是范围和验收没写，不是模型不够聪明。
