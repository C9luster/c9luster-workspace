# 09 — 选型对照与迁移

## 总对照表（模型 Wire）

| 维度 | Chat Completions | Responses | Messages | Gemini GenAI |
|------|------------------|-----------|----------|--------------|
| 端点 | `/v1/chat/completions` | `/v1/responses` | `/v1/messages` | `generateContent` |
| 对话字段 | `messages` | `input` | `messages` + 顶层 `system` | `contents` + `system_instruction` |
| 输出容器 | `choices[].message` | `output[]` items | `content[]` blocks | `candidates[].content.parts` |
| 默认状态 | 无状态 | 可 `previous_response_id` / Conversations | 无状态 | 无状态 |
| 工具循环 | 客户端编排 | 可含服务端内置工具 | 客户端编排（+ server tools） | 客户端编排 |
| 生态广度 | ★★★★★ | ★★★ | ★★★★（Claude 生态） | ★★★★（Google 生态） |
| 典型强项 | 可移植 | Agent 内置工具 | thinking / cache | 原生多模态 / GCP |

## 云封装对照

| 维度 | Bedrock Converse | Azure OpenAI |
|------|------------------|--------------|
| 统一多模型 | 强 | 主要是 OpenAI 模型家族 |
| 协议形状 | AWS 消息 API（另有 OpenAI 兼容面） | 近 OpenAI |
| 企业能力 | IAM、Guardrails、区域 | AAD、私有网络、内容过滤 |

## 决策树

```text
是否必须跨多家模型、少改代码？
  ├─ 是 → Chat Completions（+ 可选网关）
  └─ 否 → 主供应商是谁？
            ├─ OpenAI，且要内置工具/会话链 → Responses
            ├─ Anthropic / Claude 原生能力 → Messages
            ├─ Google Gemini / Vertex → GenAI
            └─ 云上多模型 + 治理 → Bedrock Converse（或对应云统一 API）
```

需要 Agent 工具标准化或 Agent 间协作时，**叠加** MCP / A2A，而不是用它们替换上表。

## 迁移清单

### A. Chat Completions → Messages

- [ ] 抽出 system 到顶层  
- [ ] `max_tokens` 设为必填  
- [ ] 工具 schema 改成 `name` + `input_schema`  
- [ ] `role:tool` 改为 `tool_result` blocks  
- [ ] 流式解析改为 Anthropic event 状态机  
- [ ] 验证消息角色严格交替  

### B. Chat Completions → Responses

- [ ] `messages` 映射为 `input` / `instructions`  
- [ ] 响应解析改为遍历 `output` items  
- [ ] 决定是否使用 `previous_response_id` 与 `store`  
- [ ] 区分内置工具与本地 function  
- [ ] 确认上游真的实现了 Responses，而不是仅有 Chat Completions  

### C. 任意原生 → Chat Completions 兼容网关

- [ ] 列出会丢失的能力（thinking、cache、内置工具…）  
- [ ] 对 tools + stream 做契约测试  
- [ ] 统一 usage 字段与错误码  
- [ ] 延迟预算计入额外一跳  

### D. 直连 → Bedrock Converse

- [ ] 改用 Converse message/content 结构  
- [ ] 配置 guardrail 与 IAM  
- [ ] 流式改用 AWS 事件流客户端  
- [ ] 核对模型是否支持所需 modalities / tools  

## 能力无损性经验法则

| 需求 | 更稳妥的协议选择 |
|------|------------------|
| 最大可移植 | Chat Completions |
| Claude extended thinking | Messages 原生 |
| OpenAI 内置 computer/web | Responses 原生 |
| GCP 治理 + Gemini | Vertex + GenAI |
| 多模型企业护栏 | Bedrock Converse 等平台 API |

**经兼容层调用「能跑」≠「语义完整」。** 评测 scaffold、计费对比、安全审计场景尤其要警惕隐藏改写。

## 测试最小集（建议）

对每个准备上线的「客户端协议 × 上游」组合，至少覆盖：

1. 单轮文本  
2. 多轮带历史  
3. 单 tool call + 结果回灌  
4. 并行 tool calls（若宣称支持）  
5. 流式文本  
6. 流式 tool arguments 拼接  
7. 多模态（若需要）  
8. JSON / schema 约束（若需要）  
9. 取消/超时  
10. 空响应与内容过滤
