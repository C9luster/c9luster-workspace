# 07 — 兼容层与网关

## 一句话定义

兼容层 / AI 网关把 **一种对外协议**（多数是 Chat Completions）翻译成 **多家上游原生协议**，并附带路由、限流、观测、兜底。它们降低接入成本，但不是无损的协议等价。

## 常见形态

| 形态 | 例子（公开产品/项目） | 典型对外协议 |
|------|----------------------|--------------|
| 开源翻译代理 | LiteLLM 等 | Chat Completions |
| 商业 AI Gateway | Portkey 等 | 多协议进出 + 观测 |
| 本地推理服务器 | vLLM、Ollama、SGLang… | 多为 Chat Completions |
| 聚合路由 | OpenRouter 等 | Chat Completions 为主 |
| IR 双向转换库 | LLM-Rosetta 等 | 库内 IR，而不是新 wire |

## 「OpenAI 兼容」的精确含义

通常承诺：

```text
POST /v1/chat/completions
Authorization: Bearer …
Body: { model, messages, … }
→ { choices: [{ message: … }], usage: … }
```

**不默认承诺：**

| 能力 | 为什么常丢 |
|------|------------|
| `/v1/responses` | 很多网关根本没实现 items / 内置工具 |
| Anthropic `thinking` 块 | Chat Completions 没有对应一等字段 |
| `cache_control` | 翻译时难保语义 |
| Gemini safety / grounding 细节 | 目标 schema 表达力不够 |
| 精确 token 计费字段 | 上游 usage 字段名与计费口径不同 |

口诀：**兼容的是形状，不保证能力全集。**

## 翻译会发生什么

以「对外 Chat Completions → 对内 Anthropic Messages」为例：

```text
messages 里的 system  ──► 顶层 system
role=tool            ──► tool_result block
tool_calls.arguments ──► tool_use.input（字符串→对象）
stream delta.content ──► content_block_delta
```

反向亦然。每一跳都可能：

- 丢弃无法表达的字段
- 改写 stop_reason / finish_reason 枚举
- 把并行 tool call 顺序或 id 策略改掉
- 在流式场景缓冲后再转发（改变首 token 延迟）

## 多协议网关（进阶）

更完整的网关允许：

- 入站用 Messages，出站打到非 Anthropic 模型
- 入站用 Responses，出站翻译到 Chat Completions 上游

这在产品上很香，但工程上要维护 **N 种入站 × M 种出站** 的语义矩阵。评估网关时看：

1. 哪些转换是官方测试过的  
2. 流式是否逐事件映射  
3. 工具调用 round-trip 是否保留 id  
4. 失败时错误码是网关的还是上游的  

## 本地推理与「假 OpenAI」

本地引擎实现 Chat Completions 时，常见缩水：

- 不支持 tools，或只支持单 tool call
- 忽略 `response_format`
- vision part 只认本地路径或特定 base64
- usage 是估算值

把生产协议测试集（含 tools + stream + json schema）对着本地 endpoint 跑一遍，比看 README「兼容 OpenAI」可靠。

## 何时该用兼容层

- 快速试验多家模型
- 统一观测与密钥
- 框架只认一种客户端

## 何时该直连原生

- 需要 Claude thinking / 精细缓存
- 需要 OpenAI 内置 computer/web 工具语义
- 延迟预算极紧，多一跳不可接受
- 合规要求请求路径最短、可审计到原厂
