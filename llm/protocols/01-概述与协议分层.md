# 01 — 概述与协议分层

## 一句话定义

LLM 协议是「调用方与模型服务之间约定的请求/响应形状」。业界没有单一标准；应用通常在 **若干主流 wire format** 与 **若干 Agent 协作协议** 之上构建。

## 协议碎片化从哪来

早期 OpenAI Completions / Chat Completions 成为事实上的公共语言后，各家仍按产品能力演进了自己的 schema：

| 演进 | 结果 |
|------|------|
| Anthropic 把 system 提到顶层，内容改成 typed blocks | Messages API |
| Google 用 `contents`/`parts`/`candidates` | Gemini GenAI |
| OpenAI 把「一条 assistant 消息」拆成多种 output items，并内置工具循环 | Responses API |
| 云厂商要统一多模型供应商 | Bedrock Converse 等封装层 |

于是出现 O(N²) 适配问题：每多一个厂商，就要多一套请求构造、响应解析、流式映射、工具序列化。翻译层（LiteLLM、网关、LLM-Rosetta 一类 IR）的价值正在于此。

## 三层协议栈

| 层 | 解决什么 | 典型协议 |
|----|----------|----------|
| **传输层** | 字节怎么走 | HTTPS、SSE、偶见 WebSocket/gRPC |
| **模型 Wire 层** | prompt / tool / stream 的 JSON 语义 | Chat Completions、Responses、Messages、Gemini、Bedrock Converse |
| **Agent 协作层** | 工具发现、Agent 委托、跨组织发现 | MCP、A2A、ANP（IBM ACP 已并入 A2A；Zed ACP 是编辑器协议，见 08） |

它们经常被混称「LLM 协议」，但职责不同：

```text
用户任务
   → Agent 框架（可能经 A2A 委托其他 Agent）
   → 本机/远程工具（可能经 MCP）
   → 模型推理（Chat Completions / Messages / …）
```

## 模型 Wire 层：你真正在对什么编程

一次典型调用要约定四件事：

1. **对话结构**：角色名、system 放哪、多模态 part 怎么写  
2. **生成控制**：temperature、max tokens、stop、JSON schema  
3. **工具调用**：工具如何声明、模型如何返回 call、结果如何回灌  
4. **流式事件**：增量文本、工具参数增量、结束原因、usage 何时出现  

四套主流 API 对这四件事的答案不同——这也是本知识库后几篇要逐一对齐的内容。

## 「OpenAI 兼容」到底兼容什么

口语里的 OpenAI-compatible，默认几乎总是指：

- 路径像 `/v1/chat/completions`
- 请求有 `messages`
- 响应有 `choices[0].message`

**不自动包含：**

- `/v1/responses` 的 items / 内置工具语义
- Anthropic 的 `thinking` / `cache_control`
- Gemini 的 `system_instruction` / `candidates`
- 各家 reasoning / citation 的专有块

选型时把「兼容 Chat Completions」和「兼容 OpenAI 全家桶」分开说，能少踩很多坑。

## 流式：协议同是 SSE，事件不同

几乎所有厂商都用 Server-Sent Events 推增量，但：

| 维度 | 常见差异 |
|------|----------|
| 帧形态 | 纯 `data:` JSON vs 带 `event:` 类型名 |
| 增量单位 | `delta.content` vs `content_block_delta` vs `candidates[].content.parts` |
| 工具参数 | 完整 JSON 一次给 vs 分片拼字符串 |
| usage | 只在最终帧 vs 独立 usage 事件 |
| 结束 | `[DONE]` 哨兵 vs `message_stop` 类事件 |

写解析器时，按「厂商事件状态机」建模，比「假设所有 SSE 都一样」稳妥。
